SYSTEM ARCHITECTURE · 平台架构说明

Muse 平台技术架构图

Muse 不是一个「聊天框 + 大模型」，而是一个以 Agent 运行时为核心的个人智能体平台：上层是多端会话入口，中间是能规划、调用工具、派生子 Agent 的执行内核，下层是技能、连接器、长期记忆与产物系统。安全边界纵贯所有层。

安全与信任体系

纵贯 L1–L6，每一次工具调用、凭据使用与外部发送都要经过它：

  • 隔离 VM 执行环境
  • Secure Vault 凭据保险库
  • 敏感操作审批卡
  • 提示注入防御（外部内容只作数据）
  • 最小必要数据原则

一次请求的生命周期

一条用户消息不是「问一次、答一次」，而是进入一个循环：上下文先被装配（时间、身份、记忆、技能索引全部注入），模型在循环中反复推理与调用工具，直到任务完成才回复。复杂任务还会在循环内派生子 Agent 并行推进。点击步骤查看细节。

FIG.03

Agent 协作拓扑：一个主脑，多个分身

主 Agent 是唯一直接与用户对话的角色。它可以把边界清晰的子任务派生给子 Agent（深度最多 2 层）：构建器负责造产物、研究员负责查资料、执行员负责跑长流程。子 Agent 拥有隔离的上下文——看不到主会话的全部历史，只拿到任务书；完成后把结果回传主 Agent 汇总。这既保护了上下文窗口，也让并行成为可能。

ISOLATION

上下文隔离

子 Agent 不继承主会话记录，只接收一份自包含的任务书（含目标、约束、交付格式），避免无关信息污染，也避免敏感上下文扩散。

DEPTH ≤ 2

派生深度受限

主 → 子 → 孙，最多两层。深度上限防止任务无限递归拆分，保证每条执行链可追踪、可终止、成本可控。

ASYNC

异步与定时唤醒

Cron 按时钟、Hooks 按事件把 Agent 唤醒执行后台任务（如每日简报、仓库巡检）；结果按设定回送到指定聊天，或静默落盘。

FIG.04

记忆系统：文件即记忆，三级沉淀

Muse 的记忆不藏在黑箱向量库里，而是以可读、可审计的 Markdown 文件落在用户自己的工作区。左侧是写入路径（对话产生的事实逐级提炼），右侧是三级存储；每次新会话开启时，长期记忆会被装配进上下文——这就是它「记得你」的原因。

写入路径 · WRITE PATH
① 对话发生chat session

用户陈述的事实、偏好、承诺在对话中被识别。

② 记入每日日志memory/YYYY-MM-DD.md

先落流水：当天发生了什么、定了什么，原样保留细节。

③ 提炼进长期记忆MEMORY.md

经久有效的事实、偏好与承诺被精选提升，日志细节则留在原地备查。

④ 关系图谱更新memory/people · groups

人物与群组单独建页索引：他们是谁、与你的关系、相关事实。

FIG.05

安全与信任边界

一个能执行命令、读邮箱、发消息的 Agent，能力越大，边界越要硬。Muse 用四道机制把「能干活」和「不越界」同时成立：

SEC-01

执行隔离

所有命令与文件操作都跑在每用户独立的隔离虚拟机里，工作区之外不可见、不可达。产物页面运行在沙箱 iframe 中，与宿主 shell 隔离，连 alert() 这类顶层 API 都被禁用，改用页内 UI。

SEC-02

凭据保险库

密码与令牌只存 Secure Vault 与连接器托管存储，永不写进代码、文件或日志。登录验证码以 [credential:uuid] 引用的形式传递，Agent 经手的是引用而不是明文，且只能用于被授权的那一次登录。

SEC-03

提示注入防御

网页、文件、邮件、工具返回一律视为「数据」而非「指令」：数据可以塑造怎么做任务，永远不能改写做什么任务。藏在内容里的越权指令会被跳过并标记，只有用户与系统能下达任务。

SEC-04

审批与最小必要

发送消息、购买、改凭据、删数据等敏感动作需要用户在审批卡上确认；处理任务时只取用必需的最少个人信息，其余上下文不外带、不写入产物、不发往无关第三方。

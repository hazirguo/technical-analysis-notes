CNI：Kubernetes 的
网络插头标准

每个 Pod 都有自己的 IP、Pod 之间能像在同一台机器上一样直接互访——这件看起来理所当然的事，背后是 CNI（Container Network Interface）在默默干活。本教程从它诞生的背景讲起，拆开规范、跟踪一个数据包的完整旅程，再横向对比 Flannel、Calico、Cilium、Kube-OVN 等主流插件的组网方式与适用场景。

01

背景：容器网络为什么这么难

先回到没有 CNI 的年代，看看 Docker 默认网络留下了哪些坑。

容器本质上是被 network namespace 隔离起来的进程：每个容器有自己独立的网卡、IP、路由表和端口空间。隔离是好事，但立刻带来一个问题——隔离出去的网络，怎么再连回来？Docker 给出的默认答案是单机 bridge 网络：

只通单机

默认 bridge 只解决同一台宿主机内容器的互通。容器漂移到另一台机器，IP 就变了、也路由不到——而调度恰恰意味着 Pod 随时漂移。

NAT 与端口映射

跨机访问要靠宿主机 IP + 端口映射（-p 8080:80）。端口会冲突，服务发现要维护映射表，源 IP 还被 NAT 改掉，日志里查不到真实调用方。

各搞一套

每家容器平台都有自己的网络实现与接口：Docker 有 libnetwork（CNM），rkt、Mesos 各不相同。网络厂商想接入每个平台，都要重复开发一遍。

2014 年 Kubernetes 提出了一套极简而强势的网络模型（下一章细讲），但它只定「目标」，不定「实现」：谁来给 Pod 分 IP、谁来打通跨节点路由？与此同时，CoreOS 在 2015 年为 rkt 提出的 CNI 给出了答案的雏形——把「给容器接网线」这件事标准化成一组可执行文件调用。时间线：

2013Docker 普及容器，默认 bridge+ NAT 成为事实起点

单机够用，但跨主机组网、IP 管理全靠外挂方案（当年的 Weave、Flannel 等项目正是在这个背景下诞生的）。

2014Kubernetes 公布网络模型：扁平网络、Pod 独立 IP

K8s 拒绝了端口映射式的组网，要求所有 Pod 处于一个扁平地址空间、无 NAT 直连——但把实现留给了插件。

2015CoreOS 提出 CNI；Docker 推出 CNM/libnetwork

两种标准化路线之争：CNM 绑定 Docker 的守护进程模型，CNI 则只是「一组可执行文件 + JSON 配置」的约定，任何运行时都能调用。后者赢得了生态。

2016–2017CNI 进入 CNCF，Kubernetes 以 CNI 为网络插件接口

Flannel、Calico、Canal 等插件陆续 CNI 化；kubelet 通过 CNI（后经 CRI 交由运行时）为每个 Pod 调用插件。

2018 至今eBPF 数据平面崛起，CNI 成为云原生网络事实标准

Cilium 把 eBPF 带入 CNI；云厂商推出 VPC 融合型 CNI；Multus 让一个 Pod 接多张网卡成为标配能力。CNI 本身始终保持着「小接口」的克制。

一句话理解 CNI 的定位

CNI 不是某个网络实现，而是一份接口规范：它只规定「运行时在 Pod 创建/删除时，如何调用外部插件程序把网线插好/拔掉」，IP 怎么分、路由怎么通、要不要封装，全部留给插件自己决定。这份克制正是它生态繁荣的原因。

02

K8s 网络模型：先立规矩，再谈实现

CNI 插件千差万别，但都必须满足 Kubernetes 定下的这套模型——理解它，就理解了所有插件的共同目标。

三条核心要求

  1. 每个 Pod 一个独立 IP：Pod 是 IP 的最小持有单位，同一 Pod 内的容器共享这个 IP 和端口空间（它们在同一个 network namespace 里）。
  2. Pod 间无 NAT 直连：任意 Pod 可以用对方的 Pod IP 直接访问任意 Pod，不经过地址翻译；Pod 看到的自身 IP，与别人看到它的 IP 一致。
  3. 节点与 Pod 互通：每个节点上的 agent（如 kubelet、系统守护进程）也能用 Pod IP 直达所有 Pod——探活、日志、exec 都依赖这一点。

这套模型换来了什么

  • 像虚机一样的心智模型：Pod ≈ 一台小虚机，有固定语义的 IP，迁移传统应用时不用改造寻址方式。
  • 端口自由：不同 Pod 可以同时监听 80 端口，永不冲突，hostPort 从刚需变成例外。
  • Service 层解耦：在扁平 Pod 网络之上，Service/ClusterIP 用 kube-proxy 或 eBPF 做负载均衡，与底层组网互不干扰。
模型只定「What」，不定「How」

「Pod IP 必须可达」可以通过隧道封装（Overlay）、通过路由协议（BGP）、通过云厂商 VPC 路由等完全不同的方式实现，性能与运维成本天差地别——这正是第 05 章「组网路线之争」的主题。CNI 插件的核心竞争力，就在于它选了哪条路线。

03

CNI 规范 anatomy：小得惊人的接口

CNI 规范的核心可以浓缩成一句话：运行时以环境变量+标准输入的方式，调用放在 /opt/cni/bin 的可执行文件。

四个动词，就是全部接口

操作何时调用插件要做的事
ADDPod 的沙箱（pause 容器）创建后把容器接进网络：建 veth、配 IP、加路由/规则，结果（IP 等）以 JSON 返回给运行时
DELPod 删除时回收一切：删 veth、释放 IP、清理规则。必须幂等——容器可能已经不在了
CHECK运行时健康检查校验该容器的网络配置是否仍然完好
VERSION协商版本报告插件支持的 CNI 规范版本（当前主流为 1.0，较新规范已加入 GC 回收残留资源）

调用时没有守护进程、没有 RPC 长连接：运行时通过环境变量传入 CNI_COMMAND、CNI_CONTAINERID、CNI_NETNS（容器的 netns 路径）等参数，把 JSON 配置喂给插件的 stdin，插件把结果 JSON 写回 stdout。无状态、短生命周期——插件挂了不影响存量 Pod 的转发，只影响新建/删除。

一份真实的 CNI 配置

节点上 /etc/cni/net.d/ 里的配置文件决定了「用哪条插件链」。下面是桥接模式的典型写法（Flannel、Calico 等都会生成自己的版本）：

{
  "cniVersion": "1.0.0",
  "name": "mynet",
  "plugins": [
    { "type": "flannel",            // 主插件：决定组网方式
      "delegate": { "hairpinMode": true, "isDefaultGateway": true } },
    { "type": "portmap",            // 链式插件：处理 hostPort 端口映射
      "capabilities": { "portMappings": true } },
    { "type": "bandwidth",          // 链式插件：限速（annotations 驱动）
      "capabilities": { "bandwidth": true } }
  ]
}

三类插件，分工明确

主插件（Main）

负责把容器真正接进网络：创建接口、打通连通性。如 bridge、macvlan、ipvlan、ptp，以及各厂商插件的本体。

IPAM 插件

只管 IP 分配与回收，常被主插件「委托」调用。host-local 最常见（按节点网段本地分配）；还有 dhcp、static，多网卡场景常用 whereabouts 做集群级分配。

Meta 插件

自己不建网，负责编排或增强：flannel（把配置转交给 bridge）、multus（多次调用其他插件实现多网卡）、portmap、bandwidth、tuning（改 sysctl/MTU 等）。

谁在调用 CNI？

链路是：kubelet → CRI → 容器运行时（containerd / CRI-O）→ CNI 插件链。现代 Kubernetes 中 kubelet 不再直接执行 CNI，而是由运行时在创建 Pod 沙箱时完成。Pod 先启动一个 pause 容器持有 network namespace，后来的业务容器都加入这个 netns——所以 Pod 内容器共享 IP、Pod 重启业务容器不换 IP。

05

组网路线之争：封装、路由，还是交给云

跨节点时 Pod IP 往往不在物理网络的路由表里——怎么让对端找到它？业界收敛出三条路线。

① Overlay 隧道封装

把 Pod 的报文整个塞进一个新的 IP 包里（VXLAN / IPIP / Geneve），外层用节点 IP 传输，到对端节点再拆开。物理网络完全不用改，跨网段、跨机房都能跑；代价是封装开销、MTU 变小、排障要看两层报文。

② Underlay 路由（BGP）

每个节点把自己的 Pod 网段通过 BGP 协议通告给交换机/其他节点，报文以原始 Pod IP 直接在物理网络上路由。无封装、性能接近裸机、tcpdump 直观；代价是需要网络侧配合（BGP 对等、云上路由表配额等）。

③ 云 VPC 原生

Pod 直接使用云 VPC 的 IP（如 AWS VPC CNI 从 ENI 分配地址），Pod 与虚机同网段互通，天然融入安全组与 VPC 流日志；代价是受 VPC 地址数量、ENI 配额等云侧限制，且强绑定单一云厂商。

维度Overlay（VXLAN 等）BGP 路由模式云 VPC 原生
报文形态内外两层 IP 头，UDP 封装原始 Pod IP 直接转发原始 Pod IP（即 VPC IP）
性能损耗有封装/解封装开销，可被网卡卸载缓解最低，接近物理网络低，受云网络面实现影响
对底层网络要求几乎无，三层可达即可需 BGP 对等或静态路由支持必须在对应云厂商内
跨网段/跨云天然支持受限，云上常被路由表规则卡住不支持跨云
排障直观度差：要解封装才能看内层好：抓包即真实报文好，且有 VPC 流日志
代表实现Flannel VXLAN、Calico VXLAN、 Cilium OverlayCalico BGP、 Cilium Native RoutingAWS VPC CNI、阿里云 Terway、Azure CNI
混合模式是常态

很多插件支持「同节点/同网段直路由、跨网段才封装」的混合策略：Calico 的 IPIP/VXLAN 可只在跨子网时启用，Cilium 也支持按拓扑选择。选插件时不要只看「它属于哪条路线」，要看它在你的拓扑里实际走哪条路径。

主流插件全景：各显神通

同一套 CNI 接口之下，是风格迥异的实现。先看总览表，再逐个认识。

Flannel —— 简单主义的代表

CoreOS 时代的老将，设计目标只有一个：让集群通起来。它给每个节点分配一个 Pod 子网（存在 etcd 或 K8s API 中），默认用 VXLAN 后端封装转发；同网段环境可用 host-gw 直路由。它不实现 NetworkPolicy（需要策略时经典组合是 Canal = Flannel 组网 + Calico 策略）。适合：学习、小集群、对策略没需求的内部平台。

Calico —— BGP 路由派的旗手

由 Tigera 维护。核心思路是把每个节点当成一台路由器：内置 BGP 客户端（BIRD）把本节点 Pod 网段通告给全网，报文无封装直达；跨子网或云环境可用 IPIP/VXLAN 退守封装。它的 Felix 代理同时负责路由与策略执行，策略能力是全场最强梯队（支持全局策略、优先级排序、L7 之外的丰富匹配）。数据平面可选 iptables/nftables/eBPF。适合：大规模自建集群、强安全合规、裸金属。

Cilium —— eBPF 原生派

基于 eBPF 在内核里直接完成转发、负载均衡与策略（第 09 章详解）：可整体替代 kube-proxy，策略可做到 L7（HTTP 方法/路径级），自带 Hubble 可观测。组网支持 VXLAN/Geneve 隧道或原生路由（含 BGP 控制面）。已成为 CNCF 毕业项目，是当前新集群的热门默认。适合：追求性能与可观测、安全要求高、愿意拥抱较新内核的团队。

Kube-OVN —— 把「云网络」做进集群

基于 OVN/OVS 构建，国内社区主导。它不止做扁平 Pod 网络，还原生提供 VPC、子网、固定 IP、QoS、安全组等云平台式的多租户网络抽象，与 OpenStack/虚拟化生态亲和。适合：私有云、电信云、多租户平台、需要 Pod 固定 IP 的传统应用迁移。

Antrea 与云厂商 CNI

Antrea 以 Open vSwitch 为数据平面，策略与流表都落在 OVS 上，支持集群级策略与 Traceflow 排障工具，在 VMware 生态中常见。云厂商 CNI（AWS VPC CNI、阿里云 Terway、Azure CNI 等）则让 Pod 直接拿 VPC IP，Pod 与云主机、RDS、SLB 天然互通并受安全组管控——用托管 K8s 时通常没有理由不用，除非撞上 ENI/地址配额。

一个已退场的老玩家

Weave Net 曾是早期热门选择（自组 mesh + 可选加密），但其公司 Weaveworks 已于 2024 年停止运营，项目不再维护——新集群不要再选它，老集群应规划迁移。

NetworkPolicy：CNI 只负责「通」，谁负责「拦」

K8s 的网络模型默认全通——任何 Pod 能访问任何 Pod。NetworkPolicy 是官方的「防火墙规则」API，但 API 本身不执行任何事。

关键分工：API Server 只存规则，执行靠插件。如果你用的是不实现 Policy 的插件（如纯 Flannel），写了 NetworkPolicy 也不会有任何流量被拦——这是新手最常见的误解之一。切换下面的策略，看看同一个请求的结果如何变化：

交互演示 · 策略执行

场景：前端 Pod（app=web）请求后端 Pod（app=db）的 5432 端口。插件为支持 Policy 的 Calico/Cilium。

没有 NetworkPolicy 时，K8s 网络是「零信任」的反面：全网扁平、全通。这也是为什么生产集群的第一条策略往往是给命名空间加默认拒绝。

一条典型的放行策略长这样——注意它按标签选人、而非 IP，因为 Pod IP 随时会变：

# 只允许 app=web 的 Pod 访问 db 的 5432 端口
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-allow-web, namespace: prod }
spec:
  podSelector: { matchLabels: { app: db } }     # 策略作用于谁
  policyTypes: [Ingress]
  ingress:
    - from: [ { podSelector: { matchLabels: { app: web } } } ]
      ports: [ { port: 5432 } ]

原生 NetworkPolicy 只有命名空间内、基于标签与端口的 L3/L4 规则。需要全局策略、域名（FQDN） egress 控制、L7 规则时，要用各插件的扩展 CRD（Calico 的 GlobalNetworkPolicy、Cilium 的 CiliumNetworkPolicy 等）——选型时这是重要的加分项。

09

eBPF 与 Cilium：为什么数据平面在换代

传统插件的数据平面建立在 iptables 与 netfilter 之上——规则多了，它就成了瓶颈。

iptables 的老问题

  • 规则是线性链表：Service 上万时，每包要逐条匹配，延迟与 CPU 随规则数增长。
  • 更新是全量替换：kube-proxy 改一条规则要重刷整表，大集群下更新延迟可达秒级。
  • 只能看到 L3/L4：想按 HTTP 路径做策略？做不到，只能外挂代理。

eBPF 的解法

  • 在内核挂钩点运行沙箱化的字节码程序，用哈希表（BPF map）做 O(1) 查找，与规则规模基本无关。
  • 转发、负载均衡、策略在网卡驱动层（XDP/TC）就近完成，可绕过大部分协议栈。
  • 顺带获得可观测：每条流量的源、目的、策略判定都能被记录——这就是 Hubble 的数据来源。

Cilium 是这条路线的代表：它既是 CNI 插件（建网、发 IP），又可开启 kube-proxy replacement 接管 Service 负载均衡，还以 CiliumNetworkPolicy 提供 L7 策略。Calico 也提供了 eBPF 数据平面作为可选项。可以说，「插件之争」正在演变为「eBPF 数据平面之争」。但 eBPF 不是免费午餐：它对内核版本有要求（通常 5.10+ 体验才完整），排障需要 bpftrace、pwru 等新工具链，团队要为学习曲线买单。

10

多网卡与特殊场景：当一张网不够用

标准模型里一个 Pod 只有 eth0。但现实中有几类场景天生需要「多平面」。

Multus：多网卡调度员

Multus 是 Meta 插件：它读取 Pod 的 networks 注解，为 Pod 依次调用多个 CNI——主网仍走集群默认 CNI，附加网卡可由 macvlan、ipvlan、SR-IOV CNI 等创建，生成 eth1、net1… 附加 IP 的分配常配合 whereabouts 做跨节点统一管理。

SR-IOV 与硬件直通

把物理网卡的虚拟功能（VF）直接给 Pod，绕过内核协议栈，换取低延迟与高吞吐。电信云（5G UPF 等网元）、高频交易、音视频处理是典型用户；代价是与云原生弹性（漂移、混部）天然冲突。

IPv4/IPv6 双栈

K8s 原生支持双栈：Pod 同时拿到 v4/v6 地址。IPAM、路由通告、策略都要双份配置——主流插件（Calico、Cilium、Kube-OVN）均已支持，Flannel 的双栈支持相对滞后，选型时需实测。

与服务网格的分工

CNI 管 L3/L4 的「通与不通」，Istio 等服务网格管 L7 的「如何通」（熔断、灰度、mTLS）。两者是上下层关系而非竞争；Cilium 等 eBPF 方案正在把部分网格能力下沉到内核，形成新的融合形态。

排障速查：Pod 网络不通时看哪里

按「配置 → 分配 → 连通 → 策略」的顺序逐层缩小范围。

# 1. 插件本身活着吗？配置对吗？
kubectl -n kube-system get pods | grep -E "calico|cilium|flannel|kube-ovn"
cat /etc/cni/net.d/10-*.conflist          # 节点上实际生效的插件链
ls /opt/cni/bin                            # 插件二进制是否齐全

# 2. IP 分到了吗？Pod 状态卡在哪一步？
kubectl get pod <pod> -o wide              # 看 IP 列是否有值
kubectl describe pod <pod>                 # 事件里找 "FailedCreatePodSandBox" / CNI 报错
crictl pods                                # 运行时视角的沙箱状态（节点上执行）

# 3. 节点内 / 跨节点分别测，定位断点
ping <同节点 Pod IP> ; ping <跨节点 Pod IP>   # 先分清是本机问题还是跨节点问题
ip route                                   # Pod 网段路由是否存在（BGP/直路由模式）
ip -d link show flannel.1                  # Overlay 模式看 VTEP 是否存在
tcpdump -i eth0 port 8472                  # VXLAN 流量（UDP 8472）有没有出门

# 4. 通但访问被拒？查策略
kubectl get networkpolicy -A               # 有没有默认拒绝在生效
# Cilium 集群可用 hubble observe 看每条流的策略判定结果
最高频的三个坑

① MTU：Overlay 封装吃掉几十字节 MTU，忘了调小会出现「小包通、大包卡死」的灵异现象。② 网段重叠：Pod CIDR 与公司内网/VPC 网段冲突，路由被更精确的条目抢走。③ 写了 Policy 却不生效（或误杀）：插件不支持 Policy 时规则是摆设；支持时，一条默认拒绝漏了放行 DNS（kube-dns 的 53 端口）会让全站「网络不通」。

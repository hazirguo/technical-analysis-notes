给 KUBERNETES 初学者的 ISTIO 系统课

先搞懂「为什么」,再学 Istio

Istio 不是凭空出现的时髦工具——它是微服务长大之后,一堆通信难题逼出来的答案。这套教程按「问题 → 旧解法 → 新思路 → Istio 怎么做」的顺序,一步步把每个技术点讲透。

共 9 章 + 综合自测 4 个可动手操作的交互演示 前置要求:知道 Pod / Service / Deployment 是什么即可
序

开始之前:30 秒补齐前置知识

只需要这四个概念,后面的内容都建立在它们之上
Pod

K8s 调度的最小单位。一个 Pod 里可以放多个共享网络的容器——记住这一点,第 5 章的 Sidecar 就靠它。

Deployment

声明「我要跑 3 个副本」,K8s 负责让实际状态一直等于这个期望。发版、扩缩容都归它管。

Service

给一组会变的 Pod 一个固定名字和虚拟 IP。别人用名字访问,Service 在后面挑一个 Pod 转发。

Namespace

集群内的逻辑隔离空间,像文件夹一样把资源分组。Istio 的很多配置都按 Namespace 生效。

本教程的一句话主线

微服务之间要打无数通「电话」。Istio 的做法是:给每个服务配一名专职接线员(代理),再建一个总调度室统一指挥。全书都在展开这一句话。

01

微服务的烦恼:拆开容易,通信难

Istio 要解决的问题,全部诞生于这一步

1.1 从单体说起

最早的应用是一个单体(Monolith):用户、订单、支付、库存全写在一个进程里,函数之间直接调用,一次请求不出进程,没有网络问题。代价是:任何一处改动都要整体重新发布;一个模块的 Bug 能拖垮全部;想给「支付」单独扩容,只能把整个应用复制一份。

于是大家把单体按业务拆成许多小服务,每个服务独立开发、独立部署、独立扩缩——这就是微服务(Microservices)。拆完之后,进程内函数调用变成了跨进程的网络调用,麻烦随之而来。

拆分前是函数调用;拆分后,每条虚线都是一次不可靠的网络通信

1.2 拆完之后,凭空多出的七个问题

假设你的电商系统拆成了 20 个服务,一次下单要串起 6 个服务。以下问题每一个都真实存在:

问题具体长什么样
服务发现支付服务有 5 个副本,IP 还天天变。订单服务该把请求发给谁?地址簿谁来维护?
负载均衡5 个副本不能只压一个;某个副本正忙时,能不能少给它分一点?
超时与重试网络偶尔抖一下就失败,重试一次大概率能成;但对方真挂了,无限重试又会把自己拖死。
熔断库存服务挂了,订单服务每次调用都要等超时才报错,线程被占满,故障会像多米诺骨牌一样扩散。
灰度发布新版本只想给 5% 的真实用户试用,出问题立刻切回来——怎么做?
通信安全服务间默认是明文 HTTP:内容能被窃听、请求能被伪造。我怎么确认「自称支付服务」的对方真的是它?
可观测性一次请求经过 6 个服务后变慢了,到底慢在哪一环?没有上帝视角,排查全靠挨个翻日志。

1.3 第一代解法:把能力写进代码(SDK)

最直接的想法:写一个公共库,封装服务发现、重试、熔断、追踪,每个服务都引这个库。Java 生态的 Spring Cloud、Netflix OSS(Eureka、Hystrix、Ribbon)就是这条路线。它能用,但有三个硬伤:

  • 多语言重复造轮子:公司里有 Java、Go、Python、Node……每个语言都要实现一遍同样的能力,行为还很难一致。
  • 升级 = 全量发版:想把重试策略改个参数、给熔断库修个 Bug,要推动几十个团队各自升级依赖、重新上线。
  • 与业务代码耦合:业务代码里混着大量治理代码,读起来累,换框架时伤筋动骨。
关键转折

这些烦恼本质上与业务无关,是通信本身的共性问题。既然如此,能不能把它们从业务代码里搬走,下沉到基础设施层统一解决?这正是服务网格的出发点——下一章先看 K8s 已经帮我们走了多远。

本章小测

1. 微服务架构下,原来不在的问题是怎么来的?

微服务的核心代价就是「本地调用变远程调用」:超时、重试、熔断、服务发现等问题,全部源于网络的不可靠性。

2. SDK 式治理(Spring Cloud 那类)最大的硬伤是?

治理逻辑写进业务进程,意味着治理能力的每一次变化都变成一次次业务发版。服务网格要做的,就是把这层能力从进程里搬出去。
02

Kubernetes 解决了什么,又止步于哪里

Istio 不是来取代 K8s 的,而是补上它故意没做的那一层

2.1 K8s 已经给的:粗粒度通信能力

K8s 的 Service 已经解决了第一章问题清单里的头两项的一大半:

  • 服务发现:Service 提供固定虚拟 IP 和 DNS 名(payments.default.svc.cluster.local),背后的 Pod 随便生灭,调用方无感。
  • 粗粒度负载均衡:节点的 kube-proxy 用 iptables/IPVS 把流量分发到后端 Pod,策略基本是随机或轮询。
  • 自愈:Pod 挂了 Deployment 会补上,探针不通过的 Pod 会被摘出 Service 的后端列表。

如果你的诉求只是「能连上、别全压一个」,K8s 原生能力足够了。但真实生产系统的诉求往往更细。

2.2 K8s 的天花板:它只看得懂四层

网络世界有个分层模型常被引用:四层(L4)指 IP + 端口的转发,只看「寄到哪个地址」;七层(L7)指理解 HTTP/gRPC 的内容,能看路径、请求头、方法。kube-proxy 工作在四层,它眼里只有数据包,没有「请求」的概念,于是这些需求它一个都做不到:

想要的能力K8s 原生缺了会怎样
按比例灰度(90/10)✗ 只能靠副本数近似10 个副本里换 1 个 ≈ 10%,想要 1% 就得养 100 个副本
按请求头/路径路由✗「带 beta 标记的用户走新版本」无法实现
超时 / 重试 / 熔断✗只能写进业务代码,回到第 1 章的 SDK 老路
服务间加密与身份✗ 默认明文集群内网一旦被突破,流量一览无余且可伪造
请求级指标与追踪✗ 只有容器级监控知道 CPU 高,不知道哪个接口在报错
故障注入演练✗想模拟「库存服务延迟 5 秒」只能改代码或拔网线

K8s 的 Ingress 也只管南北向流量(集群外 → 集群内),而且标准字段少得可怜;服务之间互调的东西向流量才是微服务的大头,K8s 基本没管。

划清边界

K8s 管的是「把服务跑起来」(调度、扩缩、自愈);Istio 管的是「让服务好好说话」(路由、韧性、安全、观测)。两者是上下层关系,不是竞争关系——Istio 本身就跑在 K8s 之上,它的配置也以 K8s 资源的形式存在。

本章小测

1. 为什么 kube-proxy 做不了「按请求头路由」?

L4 转发只处理数据包层面的地址;要按 header、路径、比例做决策,必须有一个能解析 HTTP 语义的 L7 代理——这正是 Envoy 的位置。

2. 下面哪项是 K8s 原生已经做得很好的?

Service 给了固定入口和后端分发,这是 Istio 也复用的地基;Istio 补的是它之上的 L7 治理能力。
03

服务网格:给每个服务配一名接线员

Service Mesh 的核心思想,只有两个词:代理 + 分工

3.1 核心思想:流量先过代理

服务网格(Service Mesh)的办法非常朴素:在每个服务实例旁边放一个轻量网络代理,让所有进出流量都先经过它。业务进程不再直接和外界通话,只和身边这个代理说话;治理逻辑(重试、熔断、加密、打点)全部写在代理里。

还记得第 0 章说的吗——Pod 里可以放多个共享网络的容器。代理就以「伴生容器」的形式和业务容器住进同一个 Pod,这种模式叫 Sidecar(边车):像摩托车旁的挎斗,不抢主驾,但一路同行。这个代理在 Istio 里是 Envoy。

同一个 Pod 内 App 与 Envoy 共享网络;跨 Pod 的流量永远是 Envoy ↔ Envoy

3.2 第二个关键分工:数据面与控制面

几百个 Envoy 各自为政可不行:谁来告诉每个 Envoy「支付服务的灰度比例是 90/10」「库存服务熔断阈值是 50%」?于是网格天然分成两层,这个划分是理解一切服务网格产品的钥匙:

数据面(Data Plane)

就是Envoy 们本身。它们站在流量路径上,真正搬运每一个请求,并在搬运时执行重试、加密、打点等动作。类比:路口的交警,车流都从他们手里过。

控制面(Control Plane)

不在流量路径上。它收集你写的配置,翻译成每个 Envoy 能懂的指令并下发;还负责签发身份证书。类比:交管指挥中心,自己不拦车,只定规则、发指令。

一个常见误解

控制面挂了,业务流量不会立刻中断——Envoy 手里还有上一份配置,照常干活;只是改不了新规则、签不了新证书。反过来,数据面(某个 Envoy)挂了,只有它所在的那个 Pod 受影响。分清这两层,排障时才不会找错对象。

3.3 为什么这套设计能赢过 SDK

  • 与语言无关:Envoy 是独立进程,Java、Go、Python 服务一视同仁,行为完全一致。
  • 升级不用动业务:改治理策略 = 改控制面的配置,秒级下发到所有 Envoy,业务零发版。
  • 业务代码变干净:业务进程甚至不知道网格的存在,它发出的还是普通 HTTP 请求。

代价也要说清楚:每跳流量多过一道代理,延迟和资源开销会增加(每 Pod 多一个容器);系统组件变多,运维复杂度上升。所以网格适合服务数量多、治理需求强的场景——这是第 9 章选型判断的依据。

本章小测

1. 控制面的职责是?

控制面定规则、不碰流量;数据面(Envoy)执行规则、搬运流量。控制面短暂故障时,已有流量靠 Envoy 手中的旧配置继续工作。

2. Sidecar 能和业务容器「同住」的前提是?

Pod 内容器共享 IP 与端口空间,Envoy 才能「贴身」接管业务容器的全部进出流量。
04

Istio 架构全景:一个大脑,无数只手

Istio = 一个控制面组件 istiod + 满集群的 Envoy

4.1 认识主角们

Istio 由 Google、IBM 与 Lyft 在 2017 年发起,现为 CNCF 毕业项目。早期版本控制面有 Pilot、Galley、Citadel 等好几个组件,新版(1.5 起)已合并成一个进程 istiod,初学者只需记它一个:

组件干什么
istiod(控制面)读你写的 Istio 配置资源,翻译成 Envoy 配置并通过 xDS 协议持续下发;内置 CA,给每个工作负载签发身份证书;校验配置合法性。
Envoy Sidecar(数据面)随每个业务 Pod 注入的代理。接管进出流量,执行路由、重试、熔断、mTLS、指标上报。是 Lyft 开源、C++ 编写的 L7 代理,现属 CNCF。
Ingress Gateway本质是一个独立部署的 Envoy,站在集群门口处理南北向流量(外部请求进来)。
Egress Gateway可选。所有访问集群外部的流量从这里出,方便统一管控与审计。

补充一个词:xDS 是控制面给 Envoy 下发配置的一组协议(LDS 监听、RDS 路由、CDS 集群、EDS 端点……名字不同,套路相同)。你不需要背,记住「istiod 通过 xDS 把配置推给所有 Envoy,变更近实时生效」即可。

虚线是控制流(配置与证书),实线是数据流(业务请求)——两条线永远不要混为一谈

4.2 一次请求的完整旅程

用户在浏览器点下「下单」,请求进入集群,最终拿到响应。下面这个演示把全程拆成 6 步——点「播放」,注意请求从不直接接触业务容器,每一跳都被两边的 Envoy 经手:

动手试试

请求旅程放映机

一个外部请求从进入集群到返回响应的全过程。反复看两遍,你就理解 Istio 的流量路径了。

1
用户发起请求 —— 浏览器向集群入口发出 POST /orders,请求首先到达 Ingress Gateway。
2
网关按规则放行 —— Gateway 也是 Envoy:它按 Gateway/VirtualService 配置匹配域名与路径,决定把请求交给「订单」服务。
3
到达订单 Pod 的 Envoy —— 请求先落到 sidecar 的入站监听,Envoy 在这里做身份校验、限流与指标记录,然后才转给本机 App。
4
订单 App 处理并调用支付 —— App 只管业务逻辑,它向 payments 发起普通 HTTP 调用,却不知道这个请求会先被自己身边的 Envoy 接管。
5
Envoy ↔ Envoy 的一跳 —— 出站 Envoy 选副本、建 mTLS 加密通道;支付 Pod 的 Envoy 解密验身后交给支付 App。全程的重试、熔断、追踪都在这一段发生。
6
响应原路返回 —— 响应沿相反路径回到浏览器。两个 Envoy 各自把这一跳的耗时、状态码上报,拼成第 8 章的完整链路。
本章小测

1. 关于 istiod,下面哪句是对的?

istiod 部署在 istio-system 命名空间,通常几个副本即可服务全集群;新版 Istio 已把老版本的 Pilot/Galley/Citadel 合并进它。

2. 外部流量进入集群时,第一个接触它的 Istio 组件是?

南北向流量由 Ingress Gateway 把守;东西向流量由各 Pod 的 sidecar 互联。两者跑的都是 Envoy,只是位置和配置不同。
05

Sidecar 是怎么「住进」Pod 的

自动注入 + iptables 劫持:Istio 最精巧的一步

5.1 自动注入:你什么都不用改

你写的 Deployment 里只有一个业务容器,Pod 跑起来却有两个——多出来的 Envoy 是谁塞进去的?答案是 K8s 的准入 Webhook(MutatingAdmissionWebhook):Pod 创建前,API Server 会先问一句「有人要改这个 Pod 吗?」,Istio 的注入器就在这时把 Envoy 容器和一个初始化容器补进 Pod 的定义,然后才真正创建。

开启方式只有一行:给命名空间打上标签,之后这个空间里新建的 Pod 全部自动注入:

# 给 default 命名空间开启自动注入
kubectl label namespace default istio-injection=enabled

# 部署业务后验证:READY 2/2 说明业务容器 + Envoy 都在
kubectl get pods
# NAME                        READY   STATUS
# orders-7d9f8b6c4-x2abc      2/2     Running
为什么这件事重要

注入发生在 K8s 层面,业务镜像、业务代码、Deployment 的业务部分全都不用动。这是服务网格「对业务无侵入」承诺的兑现方式,也是它碾压 SDK 方案的关键一招。

5.2 流量劫持:iptables 改道

Envoy 住进来了,但业务容器凭什么乖乖把流量交给它?靠那个一起注入的初始化容器 istio-init:它在业务启动前先运行一次,用 iptables 规则改写本 Pod 的流量走向,改完即退出:

  • 入站流量:发往业务端口的连接被重定向到 Envoy 的入站监听(端口 15006),Envoy 检查、记录后再转交业务。
  • 出站流量:业务发出的连接被重定向到 Envoy 的出站监听(端口 15001),Envoy 选路、加密后再真正发出。
  • 防死循环:Envoy 自己发出的流量用它的专属用户 ID(1337)豁免重定向,否则它会把自己的流量再劫持给自己,无限套娃。
业务容器对此一无所知:它以为自己在直连,其实每句话都过了 Envoy 的手

补充两个细节:其一,新版 Istio 也可以让 Envoy 以 K8s 原生 Sidecar(重启策略为 Always 的 init 容器)方式运行,保证它比业务先启动、后退出;其二,还有一种 Ambient(环境)模式不用 sidecar,改用每节点一个 ztunnel 代理——是更新的演进方向,初学阶段先掌握经典 sidecar 模式即可。

本章小测

1. Envoy 容器被加进 Pod,靠的是?

注入对业务完全透明,这也是为什么老应用不用改镜像就能进网格。

2. 业务容器发出的请求为什么一定会经过 Envoy?

iptables 在网络层改道,不依赖业务配合;Envoy 自身流量靠 uid 1337 豁免,避免劫持自己造成死循环。
06

流量管理:网格最常用的本事

三个核心资源:Gateway、VirtualService、DestinationRule

6.1 先认清三个资源各管一段

资源管什么生活类比
Gateway集群入口:监听哪个域名、哪个端口,用什么协议。对外流量的门面。大楼的大门与门牌
VirtualService路由规则:请求匹配什么条件(路径、请求头),就发给哪个服务的哪个版本。可以写比例、超时、重试、故障注入。总台的分诊台
DestinationRule到达策略:给目标服务定义版本分组(subset,如 v1/v2),以及负载均衡算法、连接池、熔断(异常点驱逐)参数。科室内部的排班规则

心智模型:VirtualService 决定「去哪」,DestinationRule 决定「到了之后怎么分」。版本标签来自 Pod 的 version 标签——DestinationRule 用它把同一个 Service 的 Pod 分成 v1、v2 等子集,VirtualService 才能按比例往子集发流量。

6.2 金丝雀发布:先给 10% 的人用新版

这是网格最经典的用法。新版本 v2 上线,先切 10% 流量过去观察指标,没问题再逐步放大到 50%、100%;出问题把比例调回 0,秒级回滚。下面就是它的配置——两段 YAML,注意它们如何分工:

# DestinationRule:先把 reviews 服务的 Pod 按 version 标签分成两组
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews          # 目标 Service 的名字
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
# VirtualService:再决定流量比例 —— 90% 去 v1,10% 去 v2
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts: [reviews]
  http:
  - route:
    - destination: { host: reviews, subset: v1 }
      weight: 90
    - destination: { host: reviews, subset: v2 }
      weight: 10

6.3 不止比例:条件路由

VirtualService 的匹配条件可以细到请求头。经典用法:让内测用户(带特定 Cookie/Header)全量走新版,普通用户不受影响:

http:
- match:
  - headers:
      x-beta-user: { exact: "true" }   # 命中这条规则的请求…
  route:
  - destination: { host: reviews, subset: v2 }   # …全部去 v2
- route:                                # 其余请求走默认比例
  - destination: { host: reviews, subset: v1 }
    weight: 100

6.4 韧性三件套:超时、重试、熔断

回到第 1 章的问题清单——这三项现在全部变成配置,不写一行代码:

能力配置位置作用
超时VirtualService 的 timeout等太久就放弃,避免请求无限挂起占资源。
重试VirtualService 的 retries失败自动再试几次,可限定「只对 5xx 重试」。注意:非幂等请求(如下单)乱重试会重复执行,要谨慎。
熔断DestinationRule 的 outlierDetection某个 Pod 连续报错就把它临时踢出负载均衡池(驱逐),过一会儿再放回试试。Envoy 里这叫「异常点驱逐」,效果等同熔断。
# VirtualService 里加超时与重试
http:
- route:
  - destination: { host: reviews, subset: v1 }
  timeout: 2s
  retries:
    attempts: 3
    perTryTimeout: 0.7s
    retryOn: 5xx

6.5 故障注入:主动搞破坏来练兵

VirtualService 还能故意给一部分请求加延迟或直接返回错误,用来验证「下游挂了/慢了,我的服务扛不扛得住」——这是混沌工程的入门用法:

fault:
  delay: { percentage: { value: 50 }, fixedDelay: 5s }  # 一半请求被人为延迟 5 秒
  abort: { percentage: { value: 10 }, httpStatus: 500 } # 一成请求直接报 500
本章小测

1. 90/10 灰度发布,两个资源如何分工?

没有 DestinationRule 的 subset 定义,VirtualService 就无从引用 v1/v2——这是新手最常漏的一步。

2. 熔断(异常驱逐)的收益是?

熔断保护的是调用方和整个系统,而不是把失败变成功;扩容与补实例是 K8s/Deployment 的职责。
07

安全:先证明「我是我」,再谈「能不能进」

mTLS 加密与身份 + AuthorizationPolicy 授权

7.1 问题:内网不是保险箱

传统假设是「集群内网可信」,但只要一个容器被攻破,攻击者就能在内网里窃听所有明文流量,还能伪装成任意服务发请求。Istio 的安全目标是零信任:每一次调用,双方都要出示身份,并且全程加密——不因为「在内网」就免检。

7.2 mTLS:双向 TLS

普通 HTTPS 是单向的:客户端验证服务器证书,服务器不问客户端是谁。mTLS(Mutual TLS,双向 TLS)要求双方互验:连接建立时彼此交换证书,确认对方身份,然后用协商出的密钥加密全部内容。在网格里,这件事由两个 Envoy 自动完成:

每个工作负载一张「身份证」

Pod 启动时,Envoy 向 istiod 申请证书。istiod 内置的 CA 用 Pod 的 ServiceAccount 签发一张 X.509 证书,身份遵循 SPIFFE 规范,形如 spiffe://cluster.local/ns/default/sa/orders——身份绑定的是「哪个命名空间的哪个服务账号」,不是易变的 IP。

证书短期有效、自动轮换

证书默认有效期很短(小时级),到期前 Envoy 自动续签。没有长期密钥躺在磁盘上,泄露的窗口很小。

握手时互验,通道全程加密

两个 Envoy 建立连接时交换并验证证书,任何一方验不过就断开;之后的应用数据全部走加密通道,业务容器依然发普通 HTTP,加解密在 Envoy 层完成。

窃听者视角:明文 vs mTLS

假设攻击者已经能抓到服务之间的网络包。切换模式,看看他能读到什么。

POST /payments/charge HTTP/1.1 Host: payments Authorization: Bearer eyJhbGciOiJIUzI1NiIs… Body: {"card": "6222 0202 0000 1234", "amount": 199.00}

7.3 严格程度可以调:PeerAuthentication

模式含义什么时候用
STRICT只接受 mTLS 流量,明文一律拒绝全员进网格后的目标状态
PERMISSIVEmTLS 与明文都接受(默认值)迁移过渡期:网格外服务还能调进来
DISABLE关掉 mTLS,只用明文极少数特殊场景
# 让 payments 命名空间只接受加密流量
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: payments }
spec:
  mtls: { mode: STRICT }

7.4 授权:验完身份,再定权限

mTLS 只回答「你是谁」,回答不了「你配不配调这个接口」。AuthorizationPolicy 补上后半句:基于对方身份(服务账号)、请求路径、方法来放行或拒绝。例如:只允许订单服务调用支付服务的扣款接口:

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: allow-orders-charge, namespace: payments }
spec:
  selector: { matchLabels: { app: payments } }
  action: ALLOW
  rules:
  - from:
    - source: { principals: ["cluster.local/ns/default/sa/orders"] }  # 只有订单服务
    to:
    - operation: { methods: ["POST"], paths: ["/charge"] }          # 且只能干这一件事
串起来记

认证 = 证明身份(mTLS + 证书);授权 = 分配权限(AuthorizationPolicy)。先有可信身份,授权策略才有依据——这是 Istio 安全模型的两段式结构。

本章小测

1. mTLS 里的「双向」指的是?

普通 TLS 只验服务器;mTLS 连客户端也要出示证书。网格里两端都是 Envoy,握手、验身、加解密全自动。

2. 新集群刚引入 Istio,还没全量进网格时,PeerAuthentication 选哪种更稳妥?

PERMISSIVE 是默认值,正是为迁移期设计的;直接 STRICT 会把还没进网格的调用方全部拒之门外。
08

可观测性:网格自带「全程录像」

指标、追踪、日志 —— Envoy 在转发时顺手就记了

第 1 章的最后一个问题是「一次请求慢了,不知道慢在哪」。在网格里,请求反正要过每一跳的 Envoy,Envoy 干脆在转发时把每一跳都记录下来——业务代码不用做任何事,三类观测数据自动产生:

8.1 指标(Metrics):先看全局健康

Envoy 为每个请求上报结构化指标:谁调谁、状态码、耗时、流量大小。它们被 Prometheus 采集,在 Grafana 里画成官方仪表盘。排障时最有用的四个数(业界称黄金信号/RED):

请求量 Rate

每个服务、每个接口每秒多少请求——流量突增突降第一时间可见。

错误率 Errors

5xx 占比。灰度放量时盯着它:v2 错误率一抬头,立刻把权重调回去。

延迟 Duration

看 P50/P95/P99 分位,而不是平均值——平均会把长尾的痛苦抹平。

饱和度 Saturation

连接池排队、线程等待等「快撑不住」的信号,配合 DestinationRule 的连接池上限看。

可视化拓扑工具 Kiali 能基于这些指标画出实时服务关系图:哪个服务在调哪个、流量多大、哪里飘红——第一次打开 Kiali,通常是初学者「看见网格」的高光时刻。

8.2 追踪(Tracing):给一次请求装定位器

指标告诉你「支付服务整体变慢了」,追踪能精确到「这一次下单请求,在库存服务上耗了 800ms」。原理:请求进入网格时生成一个 trace ID,每一跳都带着它,并把「我在这一跳花了多久」记成一个 span,最后拼成一条完整时间线,交给 Jaeger 这类工具展示成火焰图式的瀑布图。

一次请求的跨度瀑布图:每一行是一跳,长度是耗时——慢的环节自己会跳出来
一个必须知道的坑

Envoy 能自动生成每一跳的 span,但「把上下游 span 串成同一条 trace」需要业务代码把追踪请求头(如 traceparent、x-b3-*)从入站请求透传到出站请求。这是网格少有的需要业务配合一点点的地方——通常框架或一行中间件就能搞定,但不做,追踪就是断的。

8.3 日志(Logs):Envoy 的访问日志

每个请求经过 Envoy 都会留一行结构化访问日志(源/目标、状态码、耗时、响应标记)。它不新鲜,但胜在统一格式、全量覆盖,出问题时和指标、追踪三方对证。

三者的分工

指标回答「有没有病」(面);追踪回答「病在哪一跳」(线);日志回答「当时到底发生了什么」(点)。Istio 的价值在于:三者的原料都由 Envoy 在数据面自动生产,你只负责接上 Prometheus / Jaeger / 日志系统去消费。

本章小测

1. 为什么网格里的业务服务「什么都不做」也有请求级指标?

这正是 Sidecar 架构的复利:治理点即观测点,代理在的地方,数据就在。

2. 链路追踪断成几截、最常见的原因是?

Envoy 各自生成 span,但串联靠 trace 上下文的透传;多数框架加一个中间件即可,漏了它,Jaeger 里就是一地孤立的 span。

9.4 核心资源速查卡

资源(Kind)所属领域一句话职责
Gateway流量定义集群入口的域名、端口与协议
VirtualService流量路由规则:匹配条件 → 目标与权重,含超时/重试/故障注入

9.5 什么时候不该上 Istio

学完要会判断,而不是逢系统就套。以下信号说明网格的收益可能抵不过成本(每跳多一层代理的延迟、多养一套控制面的运维负担):

  • 服务总数个位数,团队也小——K8s 原生能力 + 简单 SDK 足够。
  • 没有灰度、mTLS、多语言治理等具体诉求,只是「听说很火」。
  • 团队没人能读懂 Envoy 配置排障——网格出问题时,排障门槛比收益先到。

综合自测:六道题检验主线

全部答对,说明你已经建立起 Istio 的完整心智模型
综合自测

1. 用一句话概括 Istio 的解题思路,最贴切的是?

「代理执行 + 控制面指挥」就是服务网格的全部骨架,Istio 是它的代表实现。

2. 线上某 Pod 的流量行为不对,排查顺序最合理的是?

流量行为由「你写的配置 → istiod 下发 → Envoy 生效」三段决定,按这条链逐段验,比重启任何东西都快。

3. 灰度时想让「内测用户走 v2、其他人走 v1」,正确的配置是?

条件匹配是 VirtualService 的活;权重只解决比例问题,分不清「谁是谁」。

4. 关于控制面故障,正确的是?

数据面与控制面解耦的直接好处:控制面故障的影响被限制在「不能变」而不是「不能跑」。

5. 订单服务调用库存服务总超时,最先看哪个可观测数据定位?

跨服务延迟问题先看 trace 的每一跳耗时,再用指标确认是普遍现象还是个别请求。

6. 下面哪个诉求是 Istio 帮不上忙的?

Pod 的生灭调度是 K8s 的地盘。Istio 站在 K8s 之上管通信,不碰调度——分清边界,才不会用错工具。
全书收束:记住这张对照表

微服务的病 → 药方:通信不可靠 → 数据面 Envoy 就近治理(重试/熔断/超时);规则要统一改 → 控制面 istiod 集中下发;身份不可信 → mTLS 证书 + 授权策略;黑盒看不见 → Envoy 顺路上报指标、追踪、日志。Istio 不是一个功能,而是这套分工本身。

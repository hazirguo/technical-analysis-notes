eBPF 从入门到精通

从零理解内核可编程性，一路走到亲手写出沙箱网络的转发面。

本教程的终点：你能独立设计并实现一个跑在 veth 对上的 eBPF 转发面——包分类、策略放行、NAT 改写、连接跟踪、计数排障，全部在内核数据面完成。

环境基线：Linux 内核 5.10+（推荐 5.15 / 6.x）、libbpf 1.x、clang 14+。文中代码均为可编译的真实写法，命令可直接在实验机上执行。

Chapter 01 · 动机

为什么沙箱网络绕不开 eBPF

你的沙箱项目里，网络转发、流量拦截、出站管控反复出现。传统做法每一条都有代价，而 eBPF 是过去十年内核给出的统一答案。这一章先讲清楚：不用 eBPF 时你在用什么付账，以及 eBPF 到底改变了什么。

1.1 沙箱网络的四个老问题

一个典型的沙箱（Agent 沙箱、代码执行沙箱、微虚机沙箱）对网络转发面的要求大同小异：

  • 隔离：沙箱只能访问被允许的目标，默认拒绝一切出站；
  • 转发：沙箱在独立 network namespace 里，包要经 veth 对送到网关/宿主机再出去，需要 NAT 改写源地址；
  • 可观测：谁访问了什么、被拒了多少次，要能计数、能审计；
  • 性能与密度：一台宿主机跑几百个沙箱时，转发路径每多一跳、多一次拷贝，密度就掉一截。

在 eBPF 普及之前，实现这些需求的工具箱是这样的：

老办法怎么做代价
iptables / nftables在 netfilter 钩子上挂规则链做过滤与 NAT（支持 conntrack 状态匹配，nftables 还有 set/map 哈希查找）本质是"匹配—动作"的声明式规则：链式跳转与多表组织一复杂，策略的表达、维护与排障成本迅速上升；想做"按身份决策、自定义状态机、顺带统计审计"这类通用逻辑时无从下手
用户态代理（如 TPROXY + 代理进程）把流量劫持到用户态进程，进程里做策略与转发每个包两次上下文切换 + 两次拷贝；代理进程本身成了瓶颈和单点
内核模块自己写 LKM 挂钩子实现转发逻辑一个野指针整个内核 panic；跟内核版本强绑定，升级内核就要改代码、重新过测试
Open vSwitch 等专用数据面用现成的虚拟交换机转发部署重、与沙箱编排体系割裂，策略下发要再接一套控制面

1.2 eBPF 的答案：在内核里安全地跑你的代码

eBPF（extended Berkeley Packet Filter）是 Linux 内核中的一台事件驱动的虚拟机。你用 C 写一小段逻辑，clang 把它编译成 eBPF 字节码，加载进内核时先由验证器（verifier）做静态检查——证明它不会崩溃、不会死循环、不会越界访问内存——通过后再由 JIT 编译成本地机器码，挂到内核的某个挂载点（hook）上。此后每当事件发生（比如网卡收到一个包），你的代码就在内核上下文里被直接执行。

这带来三个结构性变化，正好对上 1.1 的四道题：

  • 转发不出内核：包在驱动层（XDP）或流量控制层（TC）就被处理、改写、重定向，没有用户态往返——解决性能与密度；
  • 逻辑可编程：不再是"规则条目"，而是真正的程序：查表、计数、改包头、做 NAT、维护连接状态——解决表达能力；
  • 策略与状态放在 Map 里：BPF Map 是内核与用户态共享的键值存储。控制面（你的网关/编排程序）往 Map 里写策略，数据面（BPF 程序）查 Map 执行——策略变更不用重载程序，天然适配沙箱的动态编排。
与沙箱网关的对应关系 沙箱网关里常见的机制——例如流量劫持到网关处理、按目标派生出站许可、出站做 NAT——本质都是在转发路径上做拦截 → 查策略 → 改写/放行。eBPF 把这条路径收进内核数据面：拦截点是 XDP/TC，策略是 Map，出站 NAT 是 BPF 程序里的改包逻辑。本教程最后一章会把这套东西拼成一个完整设计。

Chapter 02 · 全景

eBPF 全景：程序、挂载点与一个包的旅程

eBPF 不是一种程序，而是一个家族：挂在哪里，决定了你能拿到什么数据、能调用哪些辅助函数、能对事件做什么。这一章跟着一个数据包走完内核网络栈，把转发面相关的挂载点全部点亮。

2.1 程序的生命周期

无论哪种 eBPF 程序，一生都走这五步：

  1. 编写：用受限 C（或 Rust）写逻辑，段名 SEC("xdp") 等声明程序类型；
  2. 编译：clang 以 -target bpf 编译出 .bpf.o（ELF 文件，内含字节码、Map 定义、重定位信息）；
  3. 加载：用户态加载器调用 bpf() 系统调用，内核验证器逐指令检查安全性；
  4. 挂载（attach）：把通过验证的程序绑到 hook 上——XDP 绑网卡、kprobe 绑函数地址、tracepoint 绑静态跟踪点；
  5. 运行与卸载：事件触发即运行；卸载后若没有 pin 引用，程序与 Map 一并销毁。

2.4 两类上下文：xdp_md 与 __sk_buff

初学者最容易混淆的一点：XDP 程序拿到的是"裸包"——只有 data / data_end 两个指针指向帧内存，内核还没为它分配 sk_buff，所以快，但也没有连接、路由等任何元数据。TC 程序拿到的是 __sk_buff——包已经成型为 skb，可以读 mark、priority、入接口索引，可以调 bpf_fib_lookup 查路由表，可以 bpf_redirect 到别的设备。转发面之所以以 TC 为主力，正是因为它处在"信息足够多、又还来得及改道"的位置。

一个类比 XDP 像机场安检口的第一道门：只看证件本身，决定放行、没收还是原路弹回，快得惊人但信息最少。TC 像登机口：旅客信息已在系统里，可以改签（redirect）、升舱（改 mark）、送去别的航站楼（另一个 netns）。

本章小结

  • 挂载点决定程序类型、上下文与能力边界；网络转发面主战场是 XDP（入口）+ TC（转发）。
  • XDP 处理裸包（xdp_md），TC 处理成型的 skb（__sk_buff），后者元数据丰富得多。
  • 程序五步生命周期：编写 → 编译 → 加载（过验证器）→ 挂载 → 运行。

第一个 eBPF 程序：工具链与 CO-RE

3.2 内核态代码：drop_icmp.bpf.c

XDP 程序的骨架永远是同一套路：取指针 → 边界检查 → 解析包头 → 做决定。注意每一次解引用前的边界检查不是风格问题，是验证器的硬性要求（第 4 章细讲）。

drop_icmp.bpf.c — 丢弃所有 ICMP 包
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/icmp.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

SEC("xdp")
int xdp_drop_icmp(struct xdp_md *ctx)
{
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;                    // 帧不完整，放行（其实是坏包，交给上层丢）

    if (eth->h_proto != bpf_htons(ETH_P_IP))
        return XDP_PASS;                    // 只关心 IPv4

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;

    if (ip->protocol == IPPROTO_ICMP)
        return XDP_DROP;                    // 在驱动层直接丢弃，skb 都不会分配

    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";   // 部分 helper 要求 GPL 兼容许可证

3.3 编译、加载、验证效果

编译与挂载（先用 bpftool 把流程跑通）
clang -O2 -g -target bpf -c drop_icmp.bpf.c -o drop_icmp.bpf.o

# 挂载到网卡 eth0（generic 模式不挑驱动，实验优先；native 模式见第 6 章）
sudo ip link set dev eth0 xdp obj drop_icmp.bpf.o sec xdp

sudo bpftool prog show            # 能看到程序 id、类型、JIT 状态

3.4 现代姿势：libbpf + CO-RE + 骨架代码

bpftool 手动加载只适合实验。真实项目（包括你的沙箱网关）用 libbpf 做加载器：一个用户态程序负责打开 .bpf.o、建 Map、加载、挂载、再与 Map 交互下发策略。三个关键概念：

  • CO-RE（Compile Once – Run Everywhere）：程序读取内核结构体字段时，偏移量在目标机器上按其 BTF 信息运行时重定位。同一份 .bpf.o 不必为每个内核版本重新编译——这是 BCC 时代"部署即编译"痛点的终结。
  • vmlinux.h：由 bpftool btf dump file /sys/kernel/btf/vmlinux format c 生成，包含当前内核全部结构体定义，代替零散的内核头文件。
  • 骨架（skeleton）：bpftool gen skeleton prog.bpf.o 生成一个头文件，把"打开/加载/挂载/Map 访问"封装成 prog_bpf__open_and_load() 这类强类型函数，用户态代码像调普通库一样使用。
用户态加载器骨架（libbpf 风格，节选）
#include "drop_icmp.skel.h"   // bpftool gen skeleton 生成

int main(void)
{
    struct drop_icmp_bpf *skel = drop_icmp_bpf__open_and_load();
    if (!skel) return 1;                       // 加载失败：验证器日志在这里输出

    // 把 XDP 程序挂到 ifindex=2 的网卡上
    int ifindex = if_nametoindex("eth0");
    bpf_program__attach_xdp(skel->progs.xdp_drop_icmp, ifindex);

    // …进程常驻，期间通过 skel->maps.xxx 与内核态共享数据…
    sleep(60);
    drop_icmp_bpf__destroy(skel);
}

语言选择：加载器可以用 C（libbpf 本体）、Go（cilium/ebpf 库，Cilium 项目同款）或 Rust（libbpf-rs / aya）。内核态逻辑永远是 C（或 Rust/aya）编译的字节码；用户态加载器选什么，取决于你现有系统的技术栈——沙箱网关若是 Go/Rust 写的，加载器就用同语言的库融进去，第 10 章的实战设计即按此组织。

本章小结

  • XDP 程序套路：取 data/data_end → 逐层边界检查 → 解析 → 返回动作。
  • 实验用 bpftool/ip 命令加载即可；生产用 libbpf + 骨架代码。
  • CO-RE 靠 BTF 在加载时重定位字段偏移，实现一次编译到处运行。
Chapter 04 · 内功（上）

验证器：eBPF 的安全边界与编程纪律

验证器是 eBPF 的灵魂：它在加载时模拟执行你的字节码，追踪每个寄存器的取值范围，证明程序"最多执行有限步、只访问合法内存、类型始终自洽"。理解它的检查逻辑，是从"抄例子"到"自己写转发面"的分水岭——因为你写的大部分时间，是在和它谈判。

4.1 验证器到底在查什么

  • 内存安全：包内存访问必须先与 data_end 比较过界；Map 查表返回的指针必须先判空再解引用；栈访问不许越过 512 字节栈帧；上下文结构体只许读规定的字段。
  • 类型安全：指针和整数不能混着算。指向包的指针加一个"范围已证明有界"的整数还是包指针；包指针直接乘、除、或与另一个指针相减——拒绝。
  • 必然终止：不允许无界循环；循环必须能让验证器推断出上界（内核 5.3+ 支持有界循环，单程序指令复杂度上限 100 万条）。
  • 资源纪律：单程序最多 512 字节栈；尾调用链最多 33 层；helper 函数只能用当前程序类型被授权的那批。

    4.3 让验证器满意的六个习惯

    1. 先检查、后使用，顺序不能反：验证器是路径敏感的——在某个分支里检查过界，只对该分支成立。
    2. 用 if ((void *)(p + 1) > data_end) 的固定句式检查包边界，别自创比较方式让验证器猜不透。
    3. 变长包头别硬算偏移：IPv4 头长在 ihl 字段里，先掩码（& 0xF）把范围收窄到验证器可证明的区间，再做指针运算。
    4. 循环写成 for 且上界是常数，或改用 bpf_loop() helper（5.17+）；处理变长选项时优先想"能不能不循环"。
    5. 大结构体不要放栈上：512 字节很快用完；大块临时存储用 per-CPU 数组 Map 当"草稿纸"。
    6. Map 查表结果立刻判空：__u64 *v = bpf_map_lookup_elem(...); if (!v) return ...; 写成肌肉记忆。
    心智模型 把验证器想象成一位极其严谨但缺乏想象力的审查员：它不相信任何"显然成立"的事实，只相信能在当前路径上推导出来的事实。你的工作不是"让代码正确"，而是"让正确性可被推导"。写得过验证器的代码，往往顺带也被迫把边界情况都想清楚了——这是 eBPF 代码质量普遍不错的原因。

    本章小结

    • 验证器查四件事：内存安全、类型安全、必然终止、资源纪律。
    • 包访问先验界、Map 指针先判空、循环必有界——三大纪律。
    • 读验证日志从报错行往上倒推寄存器状态，是核心排障技能。

    Maps：数据面的状态与控制面的把手

    BPF 程序本身是无状态的纯函数，跑完一次就"忘"了。所有需要跨包保留的东西——策略表、连接状态、统计计数——都住在 Map 里。转发面的设计，一大半是 Map 的设计。

    5.1 Map 的本质

    Map 是内核管理的键值存储，两个访问面：

    • BPF 程序侧：bpf_map_lookup_elem / update_elem / delete_elem，在包处理路径上以接近内存访问的速度查表；
    • 用户态侧：通过 Map 的文件描述符用 bpf() 系统调用读写——控制面下发策略、读计数，走的就是这里。

    定义方式（现代 BTF 风格，写在 .bpf.c 里，随程序一起加载）：

    两个最常用的 Map 定义
    // 策略表：目标网段 → 动作。LRU_HASH 满时自动淘汰最久未用项，适合连接类状态
struct {
    __uint(type, BPF_MAP_TYPE_LRU_HASH);
    __uint(max_entries, 65536);
    __type(key, struct flow_key);
    __type(value, struct policy_val);
} policy_map SEC(".maps");

// 计数表：每 CPU 独立副本避免原子竞争，读时由用户态求和（写多读少的统计首选）
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 4);              // 下标 0..3 分别表示 PASS/DROP/NAT/ERR
    __type(key, __u32);
    __type(value, __u64);
} stats_map SEC(".maps");

    5.2 选型表：转发面常用的 Map 类型

    类型结构转发面典型用途
    ARRAY定长数组，下标即键计数器、按 ifindex 索引的配置、全局开关
    PERCPU_ARRAY / HASH每 CPU 一份副本高频计数：无锁无原子，吞吐拉满
    HASH任意键哈希表精确策略、会话表（条目数需可控）
    LRU_HASH满时淘汰最久未用项连接跟踪表：天然防打满，冷连接自动老化
    LPM_TRIE最长前缀匹配树按网段匹配策略：10.0.0.0/8 这类规则一条搞定
    DEVMAP / CPUMAP值是设备 / CPUXDP_REDIRECT 的目标表：把包批量送往指定网卡
    RINGBUF（5.8+）环形缓冲区向用户态上报事件：被拒连接日志、审计流（替代老的 perf buffer）
    PROG_ARRAY值是程序 fd尾调用 bpf_tail_call：把大程序拆成链（单程序复杂度上限的绕法）

    5.4 Pin：让 Map 活得比进程久

    Map 默认随引用计数归零而销毁。把 Map（或程序）pin 到 /sys/fs/bpf/ 文件系统，就能让它脱离加载器进程独立存在：网关进程重启升级时，转发面与连接状态不中断；多个程序也能通过 pin 路径共享同一张 Map。生产部署里"程序 pin + Map pin + 加载器只负责更新内容"是常见形态。

    pin 与共享

    本章小结

    • 程序无状态、Map 有状态：策略、连接、计数都设计成 Map。
    • 连接跟踪用 LRU_HASH，网段策略用 LPM_TRIE，高频计数用 PERCPU，事件上报用 RINGBUF。
    • 查表落空必须有明确默认策略；pin 让 Map 跨进程、跨重启存活。
    Chapter 06 · 武器（上）

    XDP：驱动层的高速入口

    XDP（eXpress Data Path）把 BPF 程序挂在网卡驱动的收包路径最前端——包还在 DMA 环形队列里、skb 尚未分配时就先过你的代码。这是 Linux 网络栈里能合法放逻辑的最早位置，也是它性能的来源。

    6.1 五个动作与三种模式

    动作含义典型场景
    XDP_DROP在驱动层丢弃，统计可见、上层无感DDoS 清洗、入口黑名单
    XDP_PASS交回正常协议栈不关心的包
    XDP_TX从同一网卡原路发回负载均衡回包、反射式服务
    XDP_REDIRECT送往 DEVMAP/CPUMAP 指定的设备/CPU/AF_XDP socket转发到另一网卡、送用户态高速通道
    XDP_ABORTED异常丢弃（语义同 DROP，单独计数便于排障）程序内部错误路径
    • native（驱动）模式：驱动实现了 XDP 回调（如 mlx5、i40e、virtio_net），性能全开；
    • generic（SKB）模式：在协议栈早期模拟 XDP 语义，任何网卡可用，性能打折——实验与 veth 场景常用；
    • offload 模式：程序直接跑在智能网卡上（如 Netronome），少见。

    改包能力：XDP 可以改写包头（配合 bpf_xdp_adjust_head / tail / meta 增删空间），Facebook 的 Katran 负载均衡器、Cilium 的入口加速都建立在此之上。但 XDP 没有 skb 元数据、没有完整的路由与连接跟踪上下文，所以复杂转发（如带 NAT 的沙箱出口）通常不放在 XDP 独扛，而是 XDP 做粗筛 + TC 做精细活。

    6.2 亲手感受：规则如何改变包的命运

    给每类流量选一个动作，然后放行一批混合包流，观察分流结果与计数器。把 HTTPS 设成 TX 试试——想想为什么真实系统里很少这么干（提示：回包的源/目的还没改写过）。

    6.3 在 veth 上用 XDP 的注意事项

    • veth 支持 XDP（generic 与 native 均可，native 需要对端配合 xdp_redirect 语义），但沙箱场景 veth 两端常分属不同 netns，挂载时要在对应命名空间里操作；
    • XDP 程序改包后若长度变化，记得没有 skb 的"自动修正"——校验和全靠自己调 helper 维护；
    • 入口 XDP 非常适合做沙箱的第一道粗筛：协议白名单、速率计数、异常包丢弃，剩下的交给 TC。

    本章小结

    • XDP 在驱动收包最前端运行，五种动作决定包的命运，快源于"skb 之前"。
    • 能力边界：能改包能重定向，但无 skb 元数据、无连接上下文。
    • 分工原则：XDP 粗筛，TC 精细转发——这正是第 10 章实战的布局。
    Chapter 07 · 武器（下）

    TC BPF：转发面的主力

    如果 XDP 是大门口的安检，TC（Traffic Control）BPF 就是楼内的调度中心：每个网络设备 ingress/egress 各一个挂载点，上下文是完整的 skb，能查路由、能改包、能把包重定向到任意设备——包括把包"塞进"veth 对端、送进沙箱的命名空间。Cilium 的数据面主体、几乎所有 eBPF 转发方案，都以 TC 为骨架。

    7.1 挂载方式：clsact + direct-action

    给 veth 挂上 TC BPF 程序
    # clsact 是专为 BPF 准备的 qdisc，同时提供 ingress 与 egress 两个钩子
sudo tc qdisc add dev veth-guest clsact

# da = direct-action：程序返回值直接作为动作，不再经额外的 action 对象
sudo tc filter add dev veth-guest ingress bpf da obj fwd.bpf.o sec tc/ingress
sudo tc filter add dev veth-guest egress  bpf da obj fwd.bpf.o sec tc/egress

sudo tc filter show dev veth-guest ingress   # 查看已挂载的过滤器

    现代替代方案是 tcx（内核 6.6+ 的 bpf_link 式挂载，bpf_program__attach_tcx()），生命周期与排序管理更干净；传统 tc 命令行方式则在所有存量内核上可用。本教程代码用 tc 语义讲解，libbpf 中两者可切换。

    7.2 __sk_buff 能给你什么

    字段 / 能力说明转发面用途
    skb->ifindex / ingress_ifindex当前设备 / 包进入的设备判断方向：是沙箱出站还是入站
    skb->mark32 位标记，可读写，与策略路由/iptables 互通给包打标，后续路径凭标记分流（两段式 NAT 的常用手法）
    bpf_skb_store_bytes / load_bytes按偏移读写包数据（自动处理非线性 skb）改 IP/端口——NAT 的核心动作
    bpf_l3_csum_replace / bpf_l4_csum_replace增量更新校验和改地址/端口后修 IP 头与 TCP/UDP 校验和
    bpf_redirect(ifindex, flags)把包送往另一设备；BPF_F_INGRESS 让包以"从对端收到"的姿态出现veth 对穿透：沙箱 ↔ 网关 的搬运工
    bpf_fib_lookup()在 BPF 内查 FIB 路由表，得到出口与邻居 MAC自己做转发决策而不必绕回协议栈
    bpf_skb_change_head / tail增删包头空间加封装（VXLAN/Geneve 头）做隧道转发

    7.3 一个最小转发程序

    场景：宿主机侧 veth（veth-guest）的 ingress 收到沙箱发出的包，查策略后原样重定向到网关侧设备。先求骨架，NAT 在下一章补上：

    fwd.bpf.c — TC 入口：查策略 + 重定向
    #include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

#define TC_ACT_OK   0
#define TC_ACT_SHOT 2
#define GW_IFINDEX  5        // 实际项目中由用户态在加载后写入配置 Map，不要写死

SEC("tc/ingress")
int fwd_ingress(struct __sk_buff *skb)
{
    struct ethhdr eth;
    if (bpf_skb_load_bytes(skb, 0, &eth, sizeof(eth)) < 0)
        return TC_ACT_SHOT;
    if (eth.h_proto != bpf_htons(ETH_P_IP))
        return TC_ACT_OK;                    // 非 IPv4 交回协议栈处理

    // …查 policy_map（第 5 章）：落空或 DENY → TC_ACT_SHOT…
    // …建连接跟踪、做 NAT（第 8 章）…

    // 以 ingress 姿态送入网关设备：对端看起来就像"从线上收到了这个包"
    return bpf_redirect(GW_IFINDEX, BPF_F_INGRESS);
}

char LICENSE[] SEC("license") = "GPL";
    TC 与 XDP 里读包方式不同 TC 里有两种读包姿势：像 XDP 一样用 data/data_end 直接指针访问（快，但要自己处理 skb 非线性区），或用 bpf_skb_load_bytes 按偏移拷贝（慢一点，永远安全）。改包同理：直接指针写仅限于线性区内的头，通用改法是 bpf_skb_store_bytes。转发面热路径先用 load/store 写对，第二版再优化成直接访问——顺序别反。

    本章小结

    • TC BPF 挂在每设备的 ingress/egress，上下文 __sk_buff 信息最全，是转发面主力。
    • bpf_redirect + BPF_F_INGRESS 是 veth 穿透的核心动作；fib_lookup 让 BPF 自主查路由。
    • 改包三件套：store_bytes 改字段、l3/l4_csum_replace 修校验和、change_head 做封装。
    Chapter 08 · 核心技术

    转发面三件套：分类、NAT 与连接跟踪

    把前面所有零件拼起来：一个包进入转发面后，要经历"分类 → 查策略 →（必要时）改写地址 → 记录连接 → 送出"，回程包则要"凭连接记录反向改写 → 送回"。这一章把状态机讲清楚，并在实验室里完整走一遍。

    8.1 包分类：先认出"这是什么包"

    解析顺序固定：以太网 → IP（注意 ihl 变长）→ 传输层端口。产出一个流键（flow key）：五元组 {saddr, daddr, sport, dport, proto}。后续所有查表都以它为键。解析代码的纪律来自第 4 章：每层先验界、ihl 先掩码收窄范围。

    8.2 NAT：改两个字段、修两处校验和、留一条记录

    出站 SNAT 的动作清单（以 TCP 为例）：

    1. 分配外部端口：从端口池取一个未用端口（常见做法：源端口哈希 + 冲突线性探测，或直接沿用源端口、冲突时才换）；
    2. 改写源 IP → 网关外网 IP、源端口 → 分配端口，增量更新 IP 头校验和与 TCP 校验和；
    3. 在连接跟踪表里写入正向条目 五元组 → {nat_ip, nat_port}，同时写反向条目供回程查；
    4. 回程包到达：以回程五元组查反向条目，改回目的 IP/端口，同样修两处校验和，送回沙箱。
    连接跟踪 Map 与改写（节选，TC 侧）
    struct flow_key {
    __u32 saddr, daddr;
    __u16 sport, dport;
    __u8  proto, pad[3];
};
struct nat_val { __u32 addr; __u16 port; __u16 pad; __u64 last_seen; };

struct {
    __uint(type, BPF_MAP_TYPE_LRU_HASH);
    __uint(max_entries, 262144);
    __type(key, struct flow_key);
    __type(value, struct nat_val);
} conntrack SEC(".maps");

// 改源地址的四步（偏移按已解析的 iphdr/tcphdr 位置计算）：
// 1) bpf_l3_csum_replace(skb, ipoff + offsetof(iphdr, check), old_ip, new_ip, 4);
// 2) bpf_l4_csum_replace(skb, tcpoff + offsetof(tcphdr, check), old_ip, new_ip, BPF_F_PSEUDO_HDR | 4);
// 3) bpf_l4_csum_replace(..., old_port, new_port, 2);   // 端口参与 L4 校验和
// 4) bpf_skb_store_bytes(skb, ipoff + offsetof(iphdr, saddr), &new_ip, 4, 0); 再写端口
// 顺序要点：先用旧值算增量校验和，最后才覆盖字段本身。
    NAT 的三个经典坑 ① UDP 校验和为 0（IPv4 允许）时不要"修"出一个非零错误值，要么整体重算要么保持 0；② ICMP 差错报文内嵌了原始 IP 头，NAT 后内层也要改，否则对端收到对不上的报文（进阶课题，实验阶段可先放行直通）；③ 分片包只有首片有传输层头，非首片要靠分片缓存或直接放行——生产系统（如 Cilium）对此有专门处理，入门版先明确记录这一限制。

    8.4 策略维度：不止五元组

    Map 的 value 可以任意丰富，策略可以从五元组继续往上叠：按沙箱身份（入接口 ifindex 或 cgroup id 作为键的一部分）、按网段（LPM_TRIE 最长前缀）、按速率（令牌桶状态存 per-CPU Map，超限丢弃）。"按域名放行"这类 L7 语义不在数据面解决——正确姿势是控制面解析域名后把 IP 网段下发到 LPM 策略表，数据面只认 IP。很多沙箱网关的"按域名派生出站许可"，走的正是这条工程分界线。

    本章小结

    • 转发流水线：分类（五元组）→ 策略 → NAT 改写 → 记 conntrack → redirect。
    • NAT 改写四步：先修 L3/L4 校验和（用旧值算增量），最后覆盖字段。
    • L7 语义（域名）留给控制面，数据面只执行 IP 层策略。
    Chapter 09 · 运维面

    可观测与调试：看得见的转发面

    数据面在内核里跑，出问题时没有日志文件可 tail。eBPF 的可观测要靠"设计时埋点"：计数 Map、事件 ring buffer、bpftool 内省，三件套缺一不可。这一章把排障工具箱补齐。

    9.1 第一层：计数器（永远在线）

    每个决策分支配一个计数下标：PASS / DROP_POLICY / DROP_PARSE / NAT_OK / NAT_FAIL / CT_MISS……用 PERCPU_ARRAY 实现，热路径零竞争。排障时第一句话永远是 bpftool map dump 看哪条分支在涨——涨在哪，问题就在哪。

    程序内埋点（一行宏）
    #define COUNT(idx) do { __u32 k = (idx); __u64 *c = bpf_map_lookup_elem(&stats, &k); \
                     if (c) __sync_fetch_and_add(c, 1); } while (0)
// 用法：策略拒绝时 COUNT(DROP_POLICY); return TC_ACT_SHOT;

    9.2 第二层：事件流（按需采样）

    计数回答"多少"，事件回答"是谁"。把被拒绝连接的五元组、命中策略 ID 写进 RINGBUF，用户态审计程序实时消费——这就是沙箱"出站访问审计"的标准实现。注意纪律：只上报低频的异常事件（拒绝、新建连接），高频的正常转发只计数不上报，否则 ring buffer 反噬性能。

    ring buffer 上报（内核 5.8+）
    struct { __uint(type, BPF_MAP_TYPE_RINGBUF); __uint(max_entries, 256 * 1024); } events SEC(".maps");

struct deny_evt *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
if (e) { e->key = key; e->reason = DENY_POLICY; bpf_ringbuf_submit(e, 0); }

    9.3 第三层：bpftool 内省与 printk 兜底

    命令看什么

    bpftool prog dump jited id NJIT 后的本地汇编——性能分析时用
    bpftool net show各设备上 XDP/TC 程序的挂载情况一览
    bpftool map dump name conntrack连接表当前内容，NAT 排障第一现场
    bpftool prog profile / feature probe程序热点采样 / 当前内核支持的程序与 helper 探测

    最后的兜底是 bpf_printk()：输出到 /sys/kernel/debug/tracing/trace_pipe。它开销大、会拖慢热路径，只在实验环境用，提交前必须删干净。抓包验证则用 tcpdump 在 veth 两端对照——包在哪一跳消失，问题就在哪一跳。

    9.4 转发面排障决策顺序

    1. 程序在不在？bpftool net show 确认挂载点没丢（netns 重建后 TC 挂载会消失，是高频事故源）；
    2. 包进没进程序？入口计数涨不涨；不涨 → 查路由/veth 状态；
    3. 走的哪个分支？对照计数增量定位分支；
    4. 状态对不对？dump conntrack 与 policy 两张表，与预期逐条比对；
    5. 改写对不对？两端 tcpdump 对照同一包的改前/改后字节。

    本章小结

    • 三层可观测：计数 Map（永远在线）→ ring buffer 事件（只报异常）→ bpftool 内省。
    • bpf_printk 是实验兜底，生产代码零容忍。
    • 排障顺序：挂载 → 入口计数 → 分支计数 → 表内容 → 两端抓包。
    Chapter 10 · 实战

    实战：为沙箱写一个 eBPF 转发面

    终章把所有零件装成一台机器：一个跑在宿主机上的转发面，让沙箱默认与世隔绝、按策略出站、出站经 NAT、入站只放行回程与显式映射。先给完整设计，再给分阶段落地的里程碑——按顺序做，每一阶段都是可运行、可验证的系统。

    10.1 需求与拓扑

    • 每个沙箱一个 netns + 一对 veth：沙箱侧 eth0（10.66.i.2/24），宿主机侧 veth-i；
    • 出站默认拒绝；控制面按"目标网段 + 端口"下发白名单；允许的流量 SNAT 为宿主机地址出站；
    • 入站只允许已建连接的回程包，以及控制面显式配置的端口映射（DNAT）；
    • 全程计数 + 拒绝审计；策略变更不重载程序、不中断存量连接。

    10.2 为什么这样分工

    • TC 而非 XDP 做主转发：需要 skb 的 mark、fib_lookup 与成熟的 redirect 语义；XDP 可在物理口 ingress 前加一层做粗筛（限速/黑名单），是优化项不是必需项；
    • 策略键 = (沙箱标识, 目标网段, 端口)：沙箱标识用入接口 ifindex（控制面维护映射），策略表用一张 LPM_TRIE 承载网段维度、value 里带端口位图与动作；
    • 两段式思想保留：fwd_out 里先在 policy_map 做"许可判定"、再进 NAT 段，两段之间用 skb->mark 传递"已许可"标记——与很多现有网关的两段式 NAT 设计同构，迁移心智成本低；
    • 控制面唯一写者：所有 Map 只由网关进程写，BPF 程序只读策略、写自己维护的 conntrack 与计数，避免多写者一致性问题。

    10.3 分阶段落地里程碑

    M1

    打通骨架：命名空间实验环境 + 直通转发

    用 ip netns + veth 搭出"沙箱—宿主机"一对，TC 程序只做 redirect 直通，ping/curl 双向通。本阶段验证：工具链、加载器骨架、挂载生命周期（netns 重建后如何自动补挂）。验收：关掉程序包不通、挂上即通。

    M2

    分类与策略：五元组 + LPM 白名单 + 默认拒绝

    完成包分类与 policy_map 查询：命中 ALLOW 才 redirect，否则 DROP 并计数、ring buffer 上报审计事件；控制面提供增删策略的接口。验收：白名单外地址全部被拒且审计可见，白名单内正常。

    M3

    NAT 与连接跟踪：出站 SNAT + 回程自动放行

    实现第 8 章的改写四步与 conntrack 正/反条目；沙箱以宿主机地址访问外网（先用第二个 netns 冒充外网服务做闭环测试）。验收：外部抓包看到源地址已改写；回程包正确送达；并发多连接端口不冲突；UDP 与 TCP 各测一轮。

    M4

    多沙箱与生命周期：接入真实编排

    沙箱创建/销毁时控制面自动完成 veth 建链、程序挂载（或共享程序 + 按 ifindex 分发）、策略与 CT 清理；Map 全部 pin 化，网关进程可滚动重启不丢状态。验收：并发拉起 20 个沙箱各自策略互不串扰；重启网关进程转发不中断。

    M5

    硬化与性能：把坑逐个填上

    处理第 8 章三坑（UDP 校验和、ICMP 差错、分片的明确策略）、加每沙箱速率限制（令牌桶 Map）、压测对比 iptables 方案的吞吐与 p99 时延、补齐监控告警（DROP 计数突增告警）。验收：一份压测报告 + 一份"已知限制"清单，明示不接的流量类型。

    10.4 与现成方案的关系：什么时候别自己写

    先说清边界，免得重复造轮子：

    • Cilium：K8s 场景的全功能 eBPF 网络方案（CNI、kube-proxy 替代、L7 策略）。沙箱跑在 K8s 里且需求是标准 Pod 网络时，直接用它，不要自研；
    • 自研转发面的合理场景：沙箱不是 Pod（自研运行时/微虚机/裸进程）、拓扑与策略模型特殊（如按域名派生许可、两段式出站）、或需要把转发面嵌进已有网关进程——这正是你的沙箱项目的情形；
    • 即便自研，也建议先通读 Cilium 的 bpf/ 目录：它对 NAT、分片、校验和边界情况的处理是最好的免费教材。
    毕业标准 完成 M1–M3，你就已经具备"用 eBPF 开发沙箱网络转发面"的完整能力链：分类、策略、NAT、连接跟踪、计数审计一个不少。M4/M5 是把它从"能跑"推向"敢上生产"的工程化过程。下一章自测通过后，就可以开工了。

    本章小结

    • 架构：每沙箱一对 veth，TC 双程序（出/入）+ 五张 Map + libbpf 控制面。
    • M1 直通 → M2 策略 → M3 NAT/CT → M4 编排接入 → M5 硬化，五步各自可验收。
    • K8s 标准场景优先 Cilium；特殊拓扑与策略模型才是自研的领地。

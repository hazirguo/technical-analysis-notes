01

实现边界：仓内实现与仓外集成

OpenKruise Agents 的实现分两半：控制面与入站网关在本仓库内，出站流量栈不在。官方的 Agentio 流量栈（openkruise/ztunnel、agentiod、agentio-epe 等 0.2.0 镜像）是仓库之外的部署集成，与本仓代码是契约对接关系，不是同一份实现。

✓ 本仓库实现

  • Pod 生命周期状态机（9 个 Phase）与预热池 / Claim / Pause / Resume / 批量升级 / 池扩缩
  • 17 个 CRD 的资源模型（agents 组 12 + security 组 5）
  • sandbox-manager 控制面：E2B 兼容端点、配额、多租户、流量令牌签发入口
  • 入站 filter 链：路由解析、静态 token / JWT 校验、流量唤醒
  • E2B 规则入口：allowOut / denyOut 生成 TrafficPolicy、内联 security-rules 解析入注解
  • 身份扩展点：jwtissuer 签发库、IdentityProvider 接口

✗ 仓库之外的部署集成

  • ztunnel 的 L4 抓包与本地规则执行、proxy-init 的 iptables 规则
  • DNS 捕获、FQDN 解析学习与 TTL 缓存
  • EPE 逐请求 L7 判定：MCP 工具策略、正文检查、audit 分发
  • 凭证实时注入：EPE 如何按 credentialRef 读 K8s Secret 并替换 header
  • 把 TrafficPolicy / SecurityProfile CR 编译成 xDS / 本地规则的 reconciler
  • Pod 内 ACL 防绕过（root / NET_ADMIN / SYS_ADMIN）——执行体本就不在本仓
02

整体架构与组件形态

控制面是两个独立 Deployment；数据面网关不是独立进程，而是编成 c-shared .so 与 Envoy 同进程运行，controller、waker、peer server 都寄生在网关进程内。

组件形态职责
sandbox-manager独立 Deployment（默认 1 副本，memberlist 多副本对等同步）E2B 兼容管理 API：Claim / Clone / Pause / Resume / 删除、配额、流量令牌、路由同步；监听 8080、ext-proc gRPC 9002、memberlist 7946、route refresh 7789
agent-sandbox-controller独立 Deployment（leader-elect）controller-runtime operator：注册 7 个控制器（sandbox、sandboxset、sandboxclaim、sandboxupdateops、securitytokenrefresh、commit、poolautoscaler）+ Webhook
sandbox-gateway非独立进程：c-shared .so 与 Envoy 同进程入站数据面：路由解析、鉴权、流量唤醒、ORIGINAL_DST 直连 Pod IP；镜像基于 envoyproxy/envoy:contrib-v1.37.3
sandbox-gateway-cert-initgateway 同镜像的 initContainer一次性拉取 runtime mTLS 客户端证书到共享内存卷；落盘前严格校验（大小上限、证书私钥配对、有效期、ClientAuth 用途、CA 链验签），目录 0700、私钥 0400
agent-runtimePod 内原生 sidecar（initContainer + restartPolicy Always）投递上游 envd 二进制并拉起（49983）；另含 CSI 动态挂载 storage-cli
agent-identity-provider独立 Deployment（默认不随 config/default 安装）AgentIdentity 与 AgentAuthenticationConfig 控制器，可选 OIDC discovery / JWKS 端点（8443）；其签发 RPC 尚不存在（主程序注释明示）
commit-jobCommit 控制器按需创建的一次性 Job调度到源 Pod 所在节点，挂宿主机 containerd 目录，用 nerdctl commit + push 把容器可写层固化成镜像
okactl本地 CLI（直连 K8s API，不经 manager）五条运维命令：scale sandboxset、set image、create suo、restart sandbox、status

「Sandbox 就是 Pod」的字面证据

SandboxSpec 的模板字段类型就是 corev1.PodTemplateSpec；控制器以同名、controller ownerRef 为每个 Sandbox 生成恰好一个 Pod，建 Pod 时整段复制模板 Spec（pkg/controller/sandbox/core/pod_control.go:305 generateBasePodFromSandbox）。RuntimeClass 在 api 与 pkg 的全部 Go 代码中没有任何引用：模板里写 runtimeClassName 只是随 PodSpec 被动复制，项目没有显式建模、校验或准入收紧；同样没有默认禁止 privileged、hostNetwork、NET_ADMIN 的准入逻辑。

PendingRunningPausedResumingUpgradingSucceededFailedRecyclingTerminating
03

生命周期：预热池、认领、暂停恢复、升级

预热池与 Claim

  • SandboxSet 近似 ReplicaSet 维护池，但 replicas 只数未认领实例；实例被认领时摘除 SandboxSet 的 ownerRef，池子自动补位新建。模板变更的滚动更新只作用于未认领实例，按 MaxUnavailable 删旧建新，只有 Recreate 一种策略。
  • Claim 选池按 SandboxClaim 的 templateName 同名找 SandboxSet；无库存且允许时才按模板新建 Sandbox CR。sandboxcr/claim.go TryClaimSandbox、pickAnAvailableSandbox
  • 认领的原地改造幅度比文档印象小：换镜像只改模板第一个容器的 image（SetImage 即 Containers[0].Image 赋值）再原地 patch 活 Pod，不重建；CPU / 内存 resize 先改模板、再走 pods/resize 子资源（老集群回退直接 patch）；CSI 动态挂载不是给 Pod 加 volume，而是认领完成后在沙箱内经 agent-runtime 运行时挂载，配置只落在 Sandbox 注解里。
  • 认领时序中配额记账在锁沙箱之前：lockPickedSandbox 先调 Admission.Acquire 做配额记账，再写 lock 与 owner 注解锁定实例。创建后若网络策略创建失败，API 层会反手删除沙箱，不允许无策略裸奔。create.go createNetworkPolicyForSandbox

Pause 与 Resume：只有 Stop 一条路

  • 暂停 = 删 Pod（5 秒宽限期），保留 Sandbox CR 与 PVC；暂停前 preparePausedPhase 会因外部未完成的 Checkpoint 而阻塞等待。
  • Resume：spec.paused 置 false 后按模板重建 Pod，Running 阶段先等 Pod Ready，再由 initializer 依次做 runtime 重初始化 → 安全令牌重签 → CSI 按注解重挂，完成后才发布 Ready。并发 Resume 经 first-writer-wins 去重。
  • Checkpoint 在本仓的角色是「被创建与消费的 CR」：暂停与升级路径能创建 Checkpoint CR 并轮询等其 Succeeded，但真正执行转储并回写状态的 Checkpoint 控制器不在本仓注册表内，由仓外组件（Kata / 云厂商侧）承担。普通 Resume 路径也不回放 Checkpoint 数据：恢复完全靠按模板重建 Pod。

自动暂停有四条独立触发线：

探针空闲 exec 探针结果镜像为 Sandbox 条件，闲置到点暂停、判定 fail-closed 探针定时恢复 恢复时刻须在删 Pod 前先落盘 status.schedules 绝对时刻 pauseTime / shutdownTime 网关流量唤醒 见入站一节

另有暂停保留期注解把 shutdownTime 顺延，防误删。

批量升级与池扩缩

  • SandboxUpdateOps 按 label selector 选已认领实例（同 namespace 同时只允许一个处于 Updating），把 Ops 的 spec.patch 以 strategic merge 合并进实例模板。Recreate 与 CheckpointRestore 共用同一套升级状态机，区别只在删 Pod 前是否先以 filesystem 内容建 Checkpoint、建新 Pod 时把 checkpointId 写进 Pod 注解供底层恢复可写层（且只保留镜像未变的容器的可写层）。已暂停实例走两段式：先以旧模板恢复到 ResumeSucceed，再补模板触发换 Pod。
  • PoolAutoscaler 只改 SandboxSet 的 spec.replicas：Cron 策略优先于水位策略；水位策略用观测窗口均值 + tolerance 死区计算，扩容冷却默认 60 秒、缩容 300 秒。
04

控制面：三层架构、E2B 兼容与配额

分层与仓库根 AGENTS.md 契约基本吻合：API 层 pkg/servers（路由、协议模型、校验、状态码映射）→ Manager 层 pkg/sandbox-manager（业务用例、配额编排、路由同步、流量令牌）→ Infra 层 pkg/sandbox-manager/infra（唯一具体实现 sandboxcr）。唯一越界是 API 层有 9 个文件直接 import infra 的中立类型（不调用其实现），属契约自认的遗留债务。

创建沙箱全链路（代码级）

  1. POST /v2/sandboxes 进入

    先过 CheckApiKey 中间件：认证 + 沙箱归属校验，归属不符与不存在返回同样的 404 防枚举。

  2. Controller.CreateSandbox

    模板命中走 createSandboxWithClaim。

  3. Manager.ClaimSandbox

    注入配额准入与短 ID 分配（Sonyflake 13 字符 Base32）。

  4. Infra.TryClaimSandbox

    挑池 → 配额记账 → 锁定 → 后处理：换镜像与资源、初始化 agent-runtime、CSI 挂载、等 Pod Ready。

  5. syncRoute + 写 TrafficPolicy

    回程把路由同步给对等节点，再按出站规则写 TrafficPolicy CR。

  6. convertToE2BSandbox 组装响应

    返回 201。Clone 路径同构，差别是从 Checkpoint 恢复。

  • 创建快照、列快照；列 / 查模板

05

入站：网关、路由、鉴权、唤醒

网关是 Envoy + 同进程 Go filter：CGO 构建共享库放进 Envoy 镜像，入口 main 为空函数，init 里注册 filter 工厂并拉起寄生的 controller 与 peer server。Envoy 监听 7788，对外 Service 端口 10000。点按下方任一步，查看一个请求穿过网关的完整路径。

路由表：双喂、严格递增、删除栅栏

  • 路由表在网关进程内：registry 门面 + sandboxroute.Store，key 为 sandboxID（新式 Sonyflake 13 字符 Base32 短 ID，可预测性强于随机 UUID；legacy 为 namespace--name）。后端 IP 取 Sandbox 的 Status.PodInfo.PodIP。
  • 数据双喂：controller 的 informer 投影 Sandbox CR 事件；副本间再经 /refresh HTTP 接口（7789）+ memberlist 发现（7946）同步。
  • Store 只接受 ResourceVersion 严格递增的更新；删除保留 10 分钟栅栏，防乱序事件复活已删路由。未就绪回 503；路由不存在回 502 sandbox_not_found；非 Running 且不可唤醒回 502 sandbox_not_running。

三层凭证与默认开关（安全评估重点）

层机制默认状态
控制面 API KeyX-API-Key 守 sandbox-manager 全部路由；与数据面无关，网关 filter 不校验它控制面启用；数据面不涉及
数据面静态 tokenenvd access token 写在 Sandbox 注解里、随路由表进每个网关副本；filter 的 authenticate 仅当 enable-auth 为真且路由 token 非空时，用常量时间比较校验请求头 x-access-token，不符回 401enable-auth = false
数据面 JWT traffic token双开关（网关 enable-jwt-auth 进程级为真，且单沙箱注解开启）才启用；OIDC discovery 拉 JWKS 构 verifier（只收非对称算法、强制 kid 与五个标准 claim），验后比对 claims 中 sandbox ID 与 UID 与路由双绑定，不符 403、verifier 未就绪 503 fail-closed，通过后删掉该请求头再转发enable-jwt-auth = false；且默认 provider 根本不签 JWT
  • 签发方在控制面：RefreshTrafficAccessToken 先校验沙箱归属与状态，再经 IdentityProvider 接口签发，并以 UID 做 singleflight 合并。
  • JWKS 是启动时一次性快照、无周期刷新：签发方轮换密钥后网关需重启；无吊销机制，失效只能靠过期或沙箱删除重建使 UID 变化。
  • 副本间 peer 通道默认明文（路由同步含明文 AccessToken 字段），需显式配 PEER_KEY_SECRET 与 TLS Secret 才加密。

结论：出厂默认可直达沙箱任意端口

两个数据面开关全关时，任何能连到网关且知道或猜到 sandboxID 的人都能把流量打进沙箱任意端口；Host 伪造只是选路手段，不是鉴权。短 ID 是 Sonyflake 雪花型（时间戳 + worker ID + 序列），系统明确不把 ID 当秘密——防线全在 token 上，而 token 默认没开。

流量唤醒：挂起原请求、异步 Resume、原地续传

这是入站链路最有特色的实现。前置条件缺一即回 502：

请求先过鉴权再谈唤醒（防未授权唤醒） 状态恰为 Paused listener 开启 wake-on-traffic（发版默认 true、超时 60 秒） waker 已初始化 路由带完整 ObjectKey UID 栅栏通过（防旧路由误唤醒同名重建的沙箱） 沙箱启用了 ingress 流量唤醒规则
  1. filter 挂起请求

    以独立 60 秒 context 起 goroutine，向 Envoy 返回 Running 挂起这条请求——连接不释放、客户端无感。

  2. waker 复用 manager 的 Resume

    不是网关另写一份：把 spec.paused 置假并等就绪，并按规则重设 pause 与 shutdown 超时，防刚唤醒就被回收。并发请求各自起 Wake，但 Resume 经 first-writer-wins 去重。

  3. 主动同步新路由

    成功后 waker 主动把新路由 Upsert 本地 registry 并同步 peers，不等 informer。

  4. 原地续传

    filter 再查 registry 确认 Running 后，设置同样的 ORIGINAL_DST 改写并 Continue。失败回 503 sandbox_wake_failed（响应体只给泛化文案，K8s 错误细节只进日志）。

06

出站与组网：契约在本仓，执行在仓外

Pod 组网基线

项目不实现 CNI、IPAM 或独立 netns 分配：Pod 由集群 CNI 分配 Pod IP，控制器只读 PodStatus.PodIP 同步进 Sandbox 状态。沙箱间默认互访没有项目级默认拒绝：项目不下发默认 NetworkPolicy，互通与否取决于集群 CNI 与用户自加的策略。allow-internet-access 标签只是全局策略的选择信号，本仓没有默认消费它的 GlobalTrafficPolicy。

L4（TrafficPolicy）：类型契约 + Manager 侧生成

  • 类型在 api/v1alpha1（不在 api/security）：TrafficPolicy 与 GlobalTrafficPolicy 定义 peer（CIDR、FQDN、Service、Workload）、协议与端口的有序规则契约。Priority 的排序语义在类型注释中并不自洽，实际执行语义由仓外编译器决定。状态类型有定义，但把 CR 编译为 IPSet、xDS 或 ztunnel 本地规则并回写 Programmed 状态的生产 reconciler 不在本仓。
  • 本仓实有的 L4 控制代码在 Manager 侧：E2B 的 allowOut / denyOut 经校验后由 sandboxcr/network.go 生成单沙箱 TrafficPolicy CR——GenerateName 前缀 tp-、带 Sandbox OwnerReference 以便垃圾回收、Priority 常量 100、selector 优先按 Pod 的 sandbox UID 标签、老 Pod 回退 name 标签。注释明说 selector 由树外组件执行，匹配不到 Pod 时出站限制会静默不生效。allowOut 编码为 allow 规则形成白名单结构，denyOut 编码为 reject 规则；更新走 merge patch 并删除多余重复策略，读回时从规则反解出原配置。
  • traffic-proxy 注入框架在本仓：注入点不在 Pod mutating webhook，而在 Sandbox 控制器生成 Pod 时调用 sidecarutils.InjectSandboxRuntimes，以 Sandbox.Spec.Runtimes 是否含 traffic-proxy 为开关，从部署侧 ConfigMap（sandbox-injection-config，可被 user 版同 key 覆盖）读模板追加进 PodSpec 并做同名冲突检查。代理镜像、命令与可能的 iptables init 容器都由部署模板决定，本仓没有写死一套 ztunnel 生产模板。注入后有健康探针改写：应用探针序列化进 ISTIO_KUBE_APP_PROBERS、探针改走 sidecar 的 15020 状态端口。

L7（SecurityProfile）：契约完整，执行体缺席

  • 类型契约完整：域名（必填）、路径（Prefix / Exact / RE2）、方法、端口、scheme、header、queryParam 匹配；多 Profile 按 priority 合并而非首命中；动作固定序 bypass → block → mcpToolPolicy → headerManipulation → tokenTransformation → audit——都在类型与提案文档里。但逐请求执行的 EPE 本体、Envoy egress gateway、ext_proc 客户端均不在本仓。
  • 本仓实有的 L7 输入层是 E2B 内联 security-rules：pkg/servers/e2b/securityrules.go 解析、受限校验后写入 Sandbox 注解（agents.kruise.io/security-rules），由树外组件消费编译；内联通道明确拒绝 tokenTransformation、mcpToolPolicy、audit。
  • tokenTransformation 在本仓只有契约（真实密钥在代理侧从 K8s Secret 解析、沙箱只见占位符、failStrategy 默认 Block）；按 credentialRef 读 Secret 并注入 header 的动作由仓外 EPE 执行。
  • 两个易混点：pkg/proxy 不是出站 EPE，而是 sandbox-manager 入站 Envoy 的 ext_proc 路由处理器；pkg/peers 与 pkg/peersecurity 不是策略编译器，而是 Manager 与 Gateway 的成员发现与路由同步安全。

DNS：本仓最明显的缺口

本仓与 DNS 相关的只有两点：FQDN 以 peer 形式进入 TrafficPolicy，pkg/utils/network 注释说明 traffic-extension 在运行时把 FQDN 解析为 IP。dnsCapture、DNS 查询与应答学习、TTL 缓存、集群 DNS 放行都不在本仓——FQDN 规则依赖 DNS 捕获、集群 DNS 须显式放行，这些都是树外 Agentio 数据面的行为。

身份与 CA：多条链，别混淆

  • 社区默认 IdentityProvider 只生成随机 UUID 占位 token；jwtissuer 库实现了 traffic access token 与 agent token 的签发函数，但 agent-identity-provider 主程序注释明说 issuance RPC 尚不存在，当前生产入口主要跑 AgentIdentity 与 AgentAuthenticationConfig 控制器并可选开 OIDC / JWKS 服务。
  • securitytokenrefresh 控制器刷新的是经已注册 provider 签发并传播到 runtime 的 ID token（恢复后重签也走这条），与 SecurityProfile 的第三方出站凭证注入是两回事。
  • CA 注入与出站 HTTPS 信任有关、但不是凭证注入：SecurityIdentityProviderGate 开启且沙箱启用 traffic-proxy 时，控制器把 gateway CA bundle 准备到目标命名空间，给主容器挂载 CA 文件并设 SSL_CERT_FILE，解决主容器信任网关签发 CA 的问题；它不解析 credentialRef、不把第三方 API Key 写进请求。

隔离边界结论

默认隔离就是普通 Pod 的 namespace 与 cgroup 隔离 + 用户模板自带的 PodSpec；强隔离（gVisor、Kata）只能靠模板里写 runtimeClassName 被动透传，项目无专门支持。Pod 内 ACL 的执行体不在本仓，项目也没有默认收紧 root、NET_ADMIN、SYS_ADMIN 的准入逻辑——部署方应把 NetworkPolicy、Pod Security 与运行时选型当作自己的责任。

07

在沙箱方案谱系里的位置

与 CubeSandbox、SPACE、OpenSandbox 这类自带 microVM 运行时的方案不同，OpenKruise Agents 不拥有隔离层与出站数据面。它的价值在 K8s 原生的池化交付（Claim 亚秒级）、生命周期状态机（暂停、批量升级、池扩缩）、E2B 兼容控制面与入站网关（唤醒设计是其最有特色的实现）；代价是密度、隔离与出站治理的上限，都由部署方选的运行时、CNI 与树外 Agentio 栈决定。

维度OpenKruise Agents自带 microVM 运行时的方案（CubeSandbox / SPACE 等）
隔离本体标准 K8s Pod，强度随模板与 RuntimeClass 被动透传自有 microVM / 快照运行时，隔离层自带
交付方式SandboxSet 预热池 + Claim 原地改造，亚秒级交付快照 fork / 池化 microVM
入站Envoy + Go filter 网关，含流量唤醒（本仓实现）各家自有网关
出站治理只有契约与规则入口，执行靠树外 Agentio 栈通常自带数据面
密度与治理上限由部署方的运行时、CNI、Agentio 栈决定由厂商运行时决定

01

实现边界：三个仓库的记账

OpenKruise 沙箱的完整实现分布在三个开源仓库：agents 仓出契约与控制面接点，agentio 仓出出站控制面与 L7 执行，ztunnel 仓出 L4 执行体。三者拼起来，出站链路是完整的开源实现；真正留在开源之外的只有凭证 provider 服务（部署方自备）这一件。

agents 仓 · 契约与控制面接点

  • Pod 生命周期状态机（9 个 Phase）与预热池 / Claim / Pause / Resume / 批量升级 / 池扩缩
  • 17 个 CRD 的资源模型（agents 组 12 + security 组 5），含 TrafficPolicy 与 SecurityProfile 的类型契约
  • sandbox-manager 控制面：E2B 兼容端点、配额、多租户、流量令牌签发入口
  • 入站 filter 链：路由解析、静态 token / JWT 校验、流量唤醒
  • E2B 规则入口：allowOut / denyOut 生成单沙箱 TrafficPolicy、内联 security-rules 解析入注解
  • traffic-proxy 注入框架与身份扩展点：jwtissuer 签发库、IdentityProvider 接口

agentio 仓 · 出站控制面与 L7 执行

  • 控制面 agentiod：增量 KRT 策略编译、自研 xDS（仅 Delta 推送）、内置 CA 与 SPIFFE 身份签发
  • agentiod 内的主动 DNS 解析：按引用计数解析 FQDN、按 TTL 刷新，编译时展开为 IP 下发
  • L7 执行体 EPE：自 watch 并编译 SecurityProfile，逐请求执行工具策略、正文检查、凭证替换点与 audit
  • 抓包注入：沙箱边车的 ConfigMap 模板与通用 Pod 的 webhook 注入（pkg/inject）
  • 出口网关 agentio-gateway 与网关侧连接处理器 agentio-porter
  • TrustBundleDistributor：把 MITM CA 信任包分发到各命名空间

ztunnel 仓 · L4 执行体

  • ztunnel 本体（Rust，上游 ztunnel 的 Agentio 补丁版）：沙箱侧 L4 抓包流量的本地规则判定
  • 沙箱侧 DNS 流量由 ztunnel 的 DNS capture 处理，实现在本仓
  • proxy-init 按 digest 引用、不在任何仓构建：其抓包程序即 Istio 的 istio-iptables，负责写 REDIRECT 规则
  • 唯一留在开源之外的部件：凭证 provider 服务——EPE 只透传 provider 名字，真实凭证的保管与解析由部署方自备的服务完成
02

整体架构与组件形态

控制面是两个独立 Deployment；入站数据面网关不是独立进程，而是编成 c-shared .so 与 Envoy 同进程运行，controller、waker、peer server 都寄生在网关进程内。沙箱的出站流量不经这个网关：它在 Pod 内被 traffic-proxy 抓包，先过 ztunnel 的 L4 判定，再经 HBONE 隧道送到出口网关 agentio-gateway；L7 判定不在主线上——EPE 旁挂在网关侧面，Envoy 逐请求经 ext_proc 问询、按裁决执行，字节流只过 Envoy。策略与身份由 agentiod 在旁路编译下发——下图上半画入站，下半画出站。

sandbox-gateway非独立进程：c-shared .so 与 Envoy 同进程入站数据面：路由解析、鉴权、流量唤醒、ORIGINAL_DST 直连 Pod IP；镜像基于 envoyproxy/envoy:contrib-v1.37.3

okactl本地 CLI（直连 K8s API，不经 manager）五条运维命令：scale sandboxset、set image、create suo、restart sandbox、status

「Sandbox 就是 Pod」的字面证据

SandboxSpec 的模板字段类型就是 corev1.PodTemplateSpec；控制器以同名、controller ownerRef 为每个 Sandbox 生成恰好一个 Pod，建 Pod 时整段复制模板 Spec（pkg/controller/sandbox/core/pod_control.go:305 generateBasePodFromSandbox）。RuntimeClass 在 api 与 pkg 的全部 Go 代码中没有任何引用：模板里写 runtimeClassName 只是随 PodSpec 被动复制，项目没有显式建模、校验或准入收紧；同样没有默认禁止 privileged、hostNetwork、NET_ADMIN 的准入逻辑。

03

生命周期：预热池、认领、暂停恢复、升级

预热池与 Claim

  • SandboxSet 近似 ReplicaSet 维护池，但 replicas 只数未认领实例；实例被认领时摘除 SandboxSet 的 ownerRef，池子自动补位新建。模板变更的滚动更新只作用于未认领实例，按 MaxUnavailable 删旧建新，只有 Recreate 一种策略。
  • Claim 选池按 SandboxClaim 的 templateName 同名找 SandboxSet；无库存且允许时才按模板新建 Sandbox CR。sandboxcr/claim.go TryClaimSandbox、pickAnAvailableSandbox
  • 认领的原地改造幅度比文档印象小：换镜像只改模板第一个容器的 image（SetImage 即 Containers[0].Image 赋值）再原地 patch 活 Pod，不重建；CPU / 内存 resize 先改模板、再走 pods/resize 子资源（老集群回退直接 patch）；CSI 动态挂载不是给 Pod 加 volume，而是认领完成后在沙箱内经 agent-runtime 运行时挂载，配置只落在 Sandbox 注解里。
  • 认领时序中配额记账在锁沙箱之前：lockPickedSandbox 先调 Admission.Acquire 做配额记账，再写 lock 与 owner 注解锁定实例。创建后若网络策略创建失败，API 层会反手删除沙箱，不允许无策略裸奔。create.go createNetworkPolicyForSandbox

Pause 与 Resume：只有 Stop 一条路

  • 暂停 = 删 Pod（5 秒宽限期），保留 Sandbox CR 与 PVC；暂停前 preparePausedPhase 会因外部未完成的 Checkpoint 而阻塞等待。
  • Resume：spec.paused 置 false 后按模板重建 Pod，Running 阶段先等 Pod Ready，再由 initializer 依次做 runtime 重初始化 → 安全令牌重签 → CSI 按注解重挂，完成后才发布 Ready。并发 Resume 经 first-writer-wins 去重。
  • Checkpoint 在本仓的角色是「被创建与消费的 CR」：暂停与升级路径能创建 Checkpoint CR 并轮询等其 Succeeded，但真正执行转储并回写状态的 Checkpoint 控制器不在本仓注册表内，由仓外组件（Kata / 云厂商侧）承担。普通 Resume 路径也不回放 Checkpoint 数据：恢复完全靠按模板重建 Pod。

自动暂停有四条独立触发线：

探针空闲 exec 探针结果镜像为 Sandbox 条件，闲置到点暂停、判定 fail-closed 探针定时恢复 恢复时刻须在删 Pod 前先落盘 status.schedules 绝对时刻 pauseTime / shutdownTime 网关流量唤醒 见入站一节

另有暂停保留期注解把 shutdownTime 顺延，防误删。

批量升级与池扩缩

  • SandboxUpdateOps 按 label selector 选已认领实例（同 namespace 同时只允许一个处于 Updating），把 Ops 的 spec.patch 以 strategic merge 合并进实例模板。Recreate 与 CheckpointRestore 共用同一套升级状态机，区别只在删 Pod 前是否先以 filesystem 内容建 Checkpoint、建新 Pod 时把 checkpointId 写进 Pod 注解供底层恢复可写层（且只保留镜像未变的容器的可写层）。已暂停实例走两段式：先以旧模板恢复到 ResumeSucceed，再补模板触发换 Pod。
  • PoolAutoscaler 只改 SandboxSet 的 spec.replicas：Cron 策略优先于水位策略；水位策略用观测窗口均值 + tolerance 死区计算，扩容冷却默认 60 秒、缩容 300 秒。

控制面：两层管理面协作、三层架构、E2B 兼容与配额

这套系统有两层管理面，协作方式是单向的 CR 契约：sandbox-manager 是翻译层，把 E2B 的 HTTP 语义翻译成 CR 操作；K8s apiserver 是两层之间唯一的总线与事实源，17 个 CRD 就是全部状态；agent-sandbox-controller 是执行层，把 CR 变成 Pod。manager 从不直接碰 Pod 与 kubelet——它对沙箱的全部动作都是改某个 CR 的 spec，全部观察都是读某个 CR 的 status；manager 本身无本地状态，多副本靠 memberlist 同步路由表。

manager 内部再分三层，与仓库根 AGENTS.md 契约基本吻合：API 层 pkg/servers（路由、协议模型、校验、状态码映射）→ Manager 层 pkg/sandbox-manager（业务用例、配额编排、路由同步、流量令牌）→ Infra 层 pkg/sandbox-manager/infra（唯一具体实现 sandboxcr）。唯一越界是 API 层有 9 个文件直接 import infra 的中立类型（不调用其实现），属契约自认的遗留债务。

创建沙箱全链路：七步走完一次 Claim

  1. 请求进 manager 的 API 层

    POST /sandboxes（带 templateID）先过 CheckApiKey 中间件：校验 API Key，并把 Key 所属 Team 映射成同名 K8s namespace——非管理员团队的沙箱只能落在自己团队的 namespace 里，租户隔离在这一层落成。归属校验时，归属不符与不存在返回同样的 404 防枚举。

  2. Manager 层编排，配额先行

    CreateSandbox 先校验请求（egressProxy、maskRequestHost 非空直接 400，这是 E2B 有而它不支持的字段），解析 templateID 到 SandboxTemplate CR 后走 Claim 路径，并分配短 ID（Sonyflake 13 字符 Base32）；配额在 Redis 里先核算——只有 sandbox.count、limits.cpu、limits.memory 三个维度，核算在锁沙箱之前完成，Redis 故障时 fail-open 放行。

  3. Infra 层把动作落成 CR

    TryClaimSandbox 从 SandboxSet 预热池挑一个未认领的 Sandbox，挑中的标志是改这个 Sandbox CR 的注解（加锁、写入 claim 信息）；池里没货且允许直建时，才按模板新建一个 Sandbox CR。认领后加工仍全是 CR 操作：按请求改首容器镜像、走 pods/resize 子资源调资源、初始化 agent-runtime、按注解做 CSI 运行时挂载。

  4. controller 把 CR 变成 Pod

    agent-sandbox-controller 经 informer watch 到 CR，同名建 Pod、注入 sidecar，并把 PodIP 回写到 Sandbox.Status.PodInfo。这一步完全异步：manager 不参与建 Pod，只在下一步等结果。

  5. 状态只经 CR status 回流

    manager 等 Sandbox CR 的状态变 Ready 即视为创建完成并返回——它等的是 CR status，不是 Pod 本身，两者之间没有任何直连通道。

  6. 收尾两个数据面接点

    syncRoute 把路由同步给入站网关（网关路由表由 Sandbox CR 的 informer 加副本间 /refresh 推送维护，不走 K8s Service）；再按请求的 allowOut / denyOut 生成一个单沙箱 TrafficPolicy CR 写入 apiserver，agentiod 自己 watch 编译，manager 不直连 agentiod。删除方向同理能说明分工：创建后若网络策略创建失败，API 层会主动删掉刚建的 Sandbox 回滚——在它的视角里删 CR 就等于删沙箱，Pod 回收由 controller 经 ownerRef 垃圾回收完成。

  7. 组装 E2B 响应返回 201

    convertToE2BSandbox 把 Sandbox CR 转成 E2B 的 Sandbox 对象返回。Clone（从快照建）与这条链同构，差别只是多一步从 Checkpoint CR 恢复。

唯一的例外是运维 CLI okactl：它绕过 manager、直接调 K8s API 改 CR（扩缩池、换镜像、重启沙箱）。这反过来证明 CR 层才是这套系统真实的管理面，E2B 接口只是它的一个前端。

入站：网关、路由、鉴权、唤醒

网关是 Envoy + 同进程 Go filter：CGO 构建共享库放进 Envoy 镜像，入口 main 为空函数，init 里注册 filter 工厂并拉起寄生的 controller 与 peer server。Envoy 监听 7788，对外 Service 端口 10000。点按下方任一步，查看一个请求穿过网关的完整路径。

入站流量图

路由表怎么被喂数据：informer 投影 + 副本间 /refresh 同步

网关处理每个请求只查自己进程内的路由表，不逐请求去问 apiserver——所以 Sandbox CR 的变化必须被持续灌进这张表。路由表是 registry 门面 + sandboxroute.Store，key 为 sandboxID（新式 Sonyflake 13 字符 Base32 短 ID，可预测性强于随机 UUID；legacy 为 namespace--name），后端 IP 取 Sandbox 的 Status.PodInfo.PodIP。灌注靠两条通道：

通道一 · informer 投影（慢但权威的全量来源）

  • 每个网关副本内部都跑一个 client-go informer，订阅 Sandbox CR 的增删改事件。
  • 「投影」就是把 CR 映射成路由表的形状：事件一到，只抽出路由需要的几个字段——sandboxID、Status.PodInfo.PodIP、Phase、UID、AccessToken——组装成一条瘦路由记录写进 Store，不保存整个 CR。
  • 防乱序两道闸：Store 只接受 ResourceVersion 严格递增的更新，迟到或重放的旧事件不能覆盖新状态；沙箱删除后路由先保留 10 分钟栅栏，防迟到的旧事件把已删路由「复活」。
  • 副本重启后靠这条通道从 apiserver 重建全表，保证最终一致。

通道二 · 副本间 /refresh 同步（快的增量通道）

  • 网关是多副本、前面挂负载均衡，下一个请求可能落到任何一个副本上；但每个副本的 informer 看到事件的时机有快有慢。
  • 哪个副本先学到路由变化，就经 7789 端口的 /refresh HTTP 接口立刻把这条路由推给其余全部副本；副本之间靠 memberlist（7946）互相发现。manager 在创建沙箱收尾时的 syncRoute 也往这条通道推。
  • 最典型的场景是唤醒：某副本唤醒成功后本地先 upsert 新路由并立即同步 peers，不等其他副本的 informer——否则紧接着落到别的副本的请求会查不到路由、误报 502。

两条通道的分工一句话：informer 保证最终一致与重启重建，/refresh 专治「本地刚发生的变化必须立刻全副本可见」。代价在安全上：这条 peer 通道默认明文，连路由里带的 AccessToken 都明文传，要显式配置 gossip 密钥与 TLS 证书才加密（与下方凭证一节的结论一致）。

结论：出厂默认可直达沙箱任意端口

流量唤醒：挂起原请求、异步 Resume、原地续传

这是入站链路最有特色的实现。前置条件缺一即回 502：

请求先过鉴权再谈唤醒（防未授权唤醒） 状态恰为 Paused listener 开启 wake-on-traffic（发版默认 true、超时 60 秒） waker 已初始化 路由带完整 ObjectKey UID 栅栏通过（防旧路由误唤醒同名重建的沙箱） 沙箱启用了 ingress 流量唤醒规则

    以独立 60 秒 context 起 goroutine，向 Envoy 返回 Running 挂起这条请求——连接不释放、客户端无感。

  2. waker 复用 manager 的 Resume

    不是网关另写一份：把 spec.paused 置假并等就绪，并按规则重设 pause 与 shutdown 超时，防刚唤醒就被回收。并发请求各自起 Wake，但 Resume 经 first-writer-wins 去重。

  3. 主动同步新路由

    成功后 waker 主动把新路由 Upsert 本地 registry 并同步 peers，不等 informer。

  4. 原地续传

    filter 再查 registry 确认 Running 后，设置同样的 ORIGINAL_DST 改写并 Continue。失败回 503 sandbox_wake_failed（响应体只给泛化文案，K8s 错误细节只进日志）。

出站与组网：Agentio 栈

出站栈是独立开源项目 Agentio：agents 仓出 TrafficPolicy 与 SecurityProfile 的类型契约、规则入口与注入框架，agentio 仓出控制面 agentiod 与 L7 执行体 EPE，ztunnel 仓出 L4 执行体。本节按这条三仓链路记账。

栈构成：三个仓库，一件外部服务

  • agentio 仓是自研主仓，不是 Istio 的整仓 fork：openkruise/agentio（Apache-2.0，2026-07 建仓，独立 Go module，1287 个 Go 文件加 Rust 组件）。istio.io/istio 只是 go.mod 里的伪版本依赖，仓内没有 pilot 本体，全仓只有 71 个文件被派生清单标记为源自 Istio；控制面 agentiod 是自研实现（自有 pkg/xds、pkg/compiler、pkg/security），只复用 Istio 的基础库与 Workload、Authorization 的协议定义。它的定位是为不可信的 agent 与沙箱工作负载做的流量安全控制系统：built on Istio but diverges——Istio 以服务端为中心，Agentio 把治理重心移到客户端，管一个不可信 agent 发出与接收什么。
  • ztunnel 在第三个仓库：openkruise/ztunnel 是上游 ztunnel 的 Agentio 补丁版（Rust）。agentio 仓根目录的 agentio.deps 是一份 BOM：锁定 ztunnel 补丁仓的提交 SHA（CI 按 SHA 检出编译、再打包成镜像），并按不可变 digest 引用 CNI、proxy-init 等外部镜像。proxy-init 不在任何仓构建，其抓包程序即 Istio 的 istio-iptables。
  • 分发方式：Agentio 是 Sandbox Manager chart（agents-sandbox-manager，托管在 openkruise/charts、经 openkruise.github.io/charts 分发）的可选内嵌栈，agentio.enabled 默认 false；注入侧的 trafficProxy 参数在 Sandbox Controller chart 一侧（决定 sandbox-injection-config 模板）。四个策略 CRD 随 Manager chart 以模板渲染方式安装。
  • 开发形态：建仓 4 个月 542 个提交，提交高度集中于单一作者（近 200 个提交里 197 个出自同一邮箱域名），分支名大量带 codex 前缀，属单人主导加 AI 辅助的开发形态。EPE 纯求值的性能开销在仓内没有落盘数据，仓内唯一有出处的性能数字是设计文档中 2026-10-23 的 httpcallout 整链实测。

proxy-init 抓包改道：关卡怎么设、流量怎么拐

这里的「抓包」不是抓下来看的抓包，而是拦截改道：流量不复制、不留存，只是在半路上被强制拐了个弯。分工是 proxy-init 负责写规则，ztunnel 负责站岗——业务容器全程无感、无需任何配合，这就是这套代理叫「透明」的原因。

  • 写规则的一次性 init 容器：proxy-init 是沙箱 Pod 里的 init 容器，在业务容器启动之前先运行、干完活就退出；它执行的程序是 Istio 的 istio-iptables，任务只有一个——往这个 Pod 的网络命名空间里写一批 iptables 规则。写规则需要 NET_ADMIN 权限，所以让这个一次性的 init 容器拿权限，业务容器不用拿。
  • 改道怎么发生：业务容器正常发起出站连接（如连 api.openai.com:443），它以为自己在直连；数据包刚出容器、走到内核 netfilter 的 OUTPUT 链时，撞上预先写好的 REDIRECT 规则，目的地被改写为本机的 15006 端口（ztunnel 的出站口）。ztunnel 从连接的原始目的地信息（SO_ORIGINAL_DST）里读出「它本来要去哪」，查 TrafficPolicy 做 L4 判定，再决定直通转发、走 HBONE 去网关、还是就地拒绝。规则写在 Pod 共享的网络命名空间里，对 Pod 内所有容器统一生效。
  • 防自噬的三个细节：ztunnel 以固定 UID 1337 运行，规则带 owner 匹配，ztunnel 自己发出的流量不再被抓，否则它转发出去的包会再次被拐回来、无限循环；15090、15021、15020 写在排除名单里（代理自身的运维、监控与探针端口），保证 K8s 健康探针能按改写后的路径工作、代理的管理口不被自己拦截。
  • 这道关卡的软肋：规则本质上是 Pod 内的 iptables，业务容器若拿到 privileged 或 NET_ADMIN，就能自己改规则把关卡拆掉——它防的是普通工作负载，防篡改强度取决于部署方有没有收紧 Pod 的权限（与隔离边界一节的结论一致）。

Pod 组网基线

项目不实现 CNI、IPAM 或独立 netns 分配：Pod 由集群 CNI 分配 Pod IP，控制器只读 PodStatus.PodIP 同步进 Sandbox 状态。沙箱间默认互访没有项目级默认拒绝：项目不下发默认 NetworkPolicy（没有默认 NetworkPolicy 模板），互通与否取决于集群 CNI 与用户自加的策略。

L4（TrafficPolicy）：agents 出契约与生成，agentiod 编译，ztunnel 执行

  • 类型在 agents 仓的 api/v1alpha1（不在 api/security）：TrafficPolicy 与 GlobalTrafficPolicy 定义 peer（CIDR、FQDN、Service、Workload）、协议与端口的有序规则契约，并定义了状态类型。
  • 编译器在 agentio 仓的 pkg/compiler，是增量维护的 KRT 图，产物有三类：给 ztunnel 的原生 agentio.security.TrafficPolicy、兼容形态的 istio.security.Authorization、以及写在 Workload Address 里的有序 PolicyReference。Priority 按升序先行（数字小者先匹配）——以 agentio 仓代码为准，agents 仓 CRD 注释的口径与此相反。
  • 策略状态回写：agentio 仓的 pkg/policystatus 是独立校验器，负责回写 TrafficPolicy 的状态条件；它回写的 Programmed 只表示策略可分发（资格），不是 xDS 已送达的 ACK，且校验器不门控数据面分发。
  • xDS 为 agentiod 的自研实现、仅 Delta ADS 增量推送：ztunnel 订阅 Address、Authorization、TrafficPolicy 与 Sandbox 四类资源；出口网关另订阅 LDS、CDS、RDS、EDS、ECDS 等。两类客户端共用 15012 端口，靠已验证的 Pod 身份加 Node 类型前缀区分。
  • agents 仓实有的 L4 控制代码在 Manager 侧：E2B 的 allowOut / denyOut 经校验后由 sandboxcr/network.go 生成单沙箱 TrafficPolicy CR——GenerateName 前缀 tp-、带 Sandbox OwnerReference 以便垃圾回收、Priority 常量 100、selector 优先按 Pod 的 sandbox UID 标签、老 Pod 回退 name 标签。selector 由 agentiod 消费，匹配不到 Pod 时出站限制会静默不生效。allowOut 编码为 allow 规则形成白名单结构，denyOut 编码为 reject 规则；更新走 merge patch 并删除多余重复策略，读回时从规则反解出原配置。
  • traffic-proxy 注入框架在 agents 仓：注入点不在 Pod mutating webhook，而在 Sandbox 控制器生成 Pod 时调用 sidecarutils.InjectSandboxRuntimes，以 Sandbox.Spec.Runtimes 是否含 traffic-proxy 为开关，从部署侧 ConfigMap（sandbox-injection-config，可被 user 版同 key 覆盖）读模板追加进 PodSpec 并做同名冲突检查；代理镜像、命令与 iptables init 容器都由部署模板决定。注入后有健康探针改写：应用探针序列化进 ISTIO_KUBE_APP_PROBERS、探针改走 sidecar 的 15020 状态端口。
  • 抓包有三种模式：沙箱边车模式（agentio chart 提供 ConfigMap 模板、由 agents 控制器在建 Pod 时套用，init 容器 agentio-init 跑 proxy-init 镜像的 istio-iptables 写 REDIRECT 规则，参数确切为 -p 15001、-z 15006、-u 1337，排除端口串含 15090、15021、15020）、通用 Pod 模式（agentio 仓 pkg/inject 的 webhook 注入）、节点 ambient 模式（CNI 加每节点 ztunnel DaemonSet，Alpha）。iptables 规则生成在 proxy-init 镜像、ztunnel 本体在 ztunnel 仓，都不在 agentio 仓。

L7（SecurityProfile）：契约在 agents 仓，执行在 agentio 仓的 EPE

EPE 是 Egress Policy Enforcer（出口策略执行器），代码在 agentio 仓的 extensions/epe——出站流量里所有「看内容做决定」的活都归它。它自己不接流量，是出口网关里 Envoy 的一个外挂裁判：Envoy 每收到一个经 HBONE 送来的请求，就通过 ext_proc 协议把请求（头、路径、方法，必要时还有 body）发给 EPE 问一句「放不放、要不要改」，EPE 给出裁决、Envoy 照着执行；调用方身份 Envoy 已经从 HBONE 隧道证书里解出来，随 ext_proc 一起带给它。它干四类事：按域名、路径、方法、header 做 L7 版黑白名单（bypass / block）；专管 MCP 协议流量、细到只准某个 agent 调某个 MCP server 的某几个工具（mcpacl）；改写请求头并做凭证替换——把请求里的占位符 ${AGENTIO_TOKEN} 换成真实 API Key，让沙箱永远接触不到真密钥（headermutation / tokentransform）；以及拿不准时同步外呼外部决策服务、流结束后异步投递审计（httpcallout / audit）。它的两个边界最容易被误解：它不保管凭证——只做「替换」这个动作，真实密钥的值由它把 provider 名字透传给外部 provider 服务解析，那个服务不在开源里；它对身份缺失默认放行——请求没有可识别的调用方身份就没有 SecurityProfile 能命中，默认放行（另有独立的目的地授权器与 fail-closed 开关，见下）。

  • 类型契约完整：域名（必填）、路径（Prefix / Exact / RE2）、方法、端口、scheme、header、queryParam 匹配；多 Profile 按 priority 合并而非首命中；动作固定序 bypass → block → mcpToolPolicy → headerManipulation → tokenTransformation → audit。
  • EPE 自己 watch 并编译 SecurityProfile CRD，不经 xDS 下发（xDS 只为它提供 TrafficPolicy 上下文）。生产 filter 链顺序写死为 bypass → block → mcpacl → headermutation → httpcallout → tokentransform → oauth2，其中 oauth2 是 0.3.0 世代新增的一环。
  • 身份缺失默认放行：默认没有身份就没有 profile 命中、请求放行；但有一个独立于 profile 的目的地授权器仍可拦截，并提供 --fail-closed-on-missing-identity 开关把默认改成拒绝。
  • agents 仓实有的 L7 输入层是 E2B 内联 security-rules：pkg/servers/e2b/securityrules.go 解析、受限校验后写入 Sandbox 注解（agents.kruise.io/security-rules）供 Agentio 数据面消费编译；内联通道明确拒绝 tokenTransformation、mcpToolPolicy、audit，这三类只能由集群侧 SecurityProfile CR 下发。
  • 凭证注入的最后一公里不在开源 EPE 里：占位符 ${AGENTIO_TOKEN} 不是 EPE 硬编码，而是 CRD 层的 CEL 选择加模板渲染生成；EPE 不 watch CredentialProvider CRD，只把 provider 名字透传给外部 provider 服务，由后者解析真实凭证。tokenTransformation 的策略与替换点在开源仓，凭证的实际保管与解析在部署方的 provider 服务（failStrategy 默认 Block）。
  • MCP 工具策略的 8MiB 上限只封顶解压后的 body；audit 是流结束后的异步有损投递，永不影响裁决；httpcallout 有完整的 Invocation 与 Decision 协议（extensions/epe/pkg/filters/httpcallout/protocol.go），是给外部决策服务的同步外呼。
  • 两个易混点：agents 仓的 pkg/proxy 不是出站 EPE，而是 sandbox-manager 入站 Envoy 的 ext_proc 路由处理器；pkg/peers 与 pkg/peersecurity 不是策略编译器，而是 Manager 与 Gateway 的成员发现与路由同步安全。

具体例子：沙箱里的 agent 调 OpenAI，规则怎么逐级匹配

把上面的分工落到一次真实调用上：沙箱里跑着一个 AI agent，要调 OpenAI 的 API。部署方事先定好三条规矩，agent 代码里只写了个占位符，真实 Key 它永远见不到——agent 发出的请求是 POST https://api.openai.com/v1/chat/completions，Authorization 头为字面的 Bearer ${AGENTIO_TOKEN}。

事前规则谁定的形态内容
出站白名单调用方建沙箱时传的 E2B allowOut: ["api.openai.com"]manager 生成单沙箱 TrafficPolicy CR只准连 api.openai.com，其余默认不通
L7 策略平台管理员SecurityProfile CR域名 api.openai.com 只许 POST /v1/chat/completions；Authorization 里的占位符要替换成真实凭证

这个例子也点出整套出站规则的匹配方式：规则定义、编译与执行是三拨不同的组件在接力——CR 是定义，agentiod 把 L4 那份编译成 IP 规则下发给 ztunnel、EPE 自己编译 L7 那份，执行则落在 ztunnel（连接级）与 Envoy + EPE（请求级）两处。任何一级的规则没配对，流量就在那一级停下，且停下的位置本身就说明了它死在哪类规则上。

DNS：主动解析，不是拦截学习

  • FQDN 的落地是 agentiod 内的主动解析：一个引用计数驱动的解析控制器，只解析仍被 TrafficPolicy 的 FQDN peer 或 AgentioConfig 引用的主机名；A 与 AAAA 独立按 TTL 提前刷新并带确定性抖动，解析结果进入编译器的 KRT 集合，FQDN peer 在下发前展开成 IP。
  • 沙箱侧的 DNS 流量本身归 ztunnel 的 DNS capture 处理，实现在 ztunnel 仓。agentio 仓内没有实现「集群 DNS 须显式放行」的对应代码。
  • agents 仓与 DNS 相关的只有两点：FQDN 以 peer 形式进入 TrafficPolicy，pkg/utils/network 注释说明 traffic-extension 在运行时把 FQDN 解析为 IP。

身份与 CA：多条链，别混淆

  • 社区默认 IdentityProvider 只生成随机 UUID 占位 token；jwtissuer 库实现了 traffic access token 与 agent token 的签发函数，但 agent-identity-provider 主程序注释明说 issuance RPC 尚不存在，当前生产入口主要跑 AgentIdentity 与 AgentAuthenticationConfig 控制器并可选开 OIDC / JWKS 服务。
  • securitytokenrefresh 控制器刷新的是经已注册 provider 签发并传播到 runtime 的 ID token（恢复后重签也走这条），与 SecurityProfile 的第三方出站凭证注入是两回事。
  • Agentio 侧的工作负载身份是 SPIFFE：ID 形如 spiffe://信任域/ns/命名空间/sa/服务账号，由 agentiod 内置 CA 经同端口的 IstioCertificateService 签发 SVID；Pod UID、含 sandbox-attester 的 role 等实例维度不进 SPIFFE 路径，而是写入证书的自定义 OID 扩展。agentiod 的 xDS 与证书签发共用 15012 端口。
  • TLS 检查的信任前提由 agentiod 的 MITM CA 满足：默认 SELF_SIGN 模式自签根，网关叶证书有效期只有 15 分钟、经 SDS 下发；工作负载侧的信任包由 TrustBundleDistributor 分发到各命名空间。
  • CA 注入与出站 HTTPS 信任有关、但不是凭证注入：SecurityIdentityProviderGate 开启且沙箱启用 traffic-proxy 时，控制器把 gateway CA bundle 准备到目标命名空间，给主容器挂载 CA 文件并设 SSL_CERT_FILE，解决主容器信任网关签发 CA 的问题；它不解析 credentialRef、不把第三方 API Key 写进请求。agents 仓的这段 CA 注入与 agentiod 的 MITM CA 是同一条链的两端。

隔离边界结论

默认隔离就是普通 Pod 的 namespace 与 cgroup 隔离 + 用户模板自带的 PodSpec；强隔离（gVisor、Kata）只能靠模板里写 runtimeClassName 被动透传，项目无专门支持。Pod 内 ACL 由 ztunnel 边车执行，其防篡改强度受 Pod 本身权限影响，而项目没有默认收紧 privileged 与 NET_ADMIN 等 capability 的准入逻辑——部署方应把 NetworkPolicy、Pod Security 与运行时选型当作自己的责任。

07

在沙箱方案谱系里的位置

与 CubeSandbox、SPACE、OpenSandbox 这类自带 microVM 运行时的方案不同，OpenKruise Agents 不拥有隔离层；出站治理由同组织的 Agentio 开源栈提供。它的价值在 K8s 原生的池化交付（Claim 亚秒级）、生命周期状态机（暂停、批量升级、池扩缩）、E2B 兼容控制面与入站网关（唤醒设计是其最有特色的实现）；代价是密度与隔离的上限由部署方选的运行时与 CNI 决定，出站治理的上限由 Agentio 栈决定。

能力记账按三个仓库分：agents 仓出 Pod 生命周期、17 个 CRD 的资源模型、Manager 控制面、E2B 规则入口、入站 filter 链与身份扩展点；agentio 仓出出站控制面（agentiod 的策略编译、xDS、CA 与 DNS 解析）与 L7 执行（EPE）；ztunnel 仓出 L4 执行体。拼起来后出站链路是完整的开源实现，真正留在开源之外的只有凭证 provider 服务（部署方自备）这一件。这条边界是本报告最重要的结论。

维度OpenKruise Agents自带 microVM 运行时的方案（CubeSandbox / SPACE 等）
隔离本体标准 K8s Pod，强度随模板与 RuntimeClass 被动透传自有 microVM / 快照运行时，隔离层自带
交付方式SandboxSet 预热池 + Claim 原地改造，亚秒级交付快照 fork / 池化 microVM
入站Envoy + Go filter 网关，含流量唤醒（本仓实现）各家自有网关
出站治理三仓开源：agents 出契约与规则入口，agentio 出编译与 L7 执行，ztunnel 出 L4 执行；仅凭证 provider 服务自备通常自带数据面
密度与治理上限密度与隔离由部署方的运行时、CNI 决定，出站治理由 Agentio 栈决定由厂商运行时决定

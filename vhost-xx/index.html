vhost 家族：把 virtio 的数据面
搬出 QEMU 的那一类设备

你在 QEMU / KVM 里见过 vhost-net、在 DPDK 里见过 vhost-user、在沙箱里见过 vhost-vsock——这一类以 vhost-* 命名的设备不是某种具体硬件，而是同一种思想的不同落点：virtio 的控制面留在模拟器里，数据面交给更靠近数据的地方执行。这一页把它们的工作原理、建立流程和适用场景一次讲透。

一句话定义：vhost = virtio 数据面卸载框架 —— 描述符环（virtqueue）仍由 Guest 内存承载，但「谁来消费队列、搬数据、发中断」从 QEMU 用户态换成了内核线程、独立进程（DPDK/SPDK），乃至网卡硬件。

01

先说清楚：纯 virtio 慢在哪

virtio 本身是一套前后端契约：Guest 里的前端驱动（如 virtio_net）把要发送的数据包地址写进共享内存中的队列，后端（模拟器）取走处理。问题是当后端是 QEMU 用户态进程时，每一个包都要付三笔税：

税一 · VM Exit

Guest 写队列通知寄存器（kick）会触发一次 VM Exit，CPU 从 Guest 模式陷入宿主机，QEMU 被调度醒来才知道「有活干了」。收包方向则反过来，QEMU 要通过 KVM 注入虚拟中断。

税二 · 进程调度与上下文切换

QEMU 是普通用户进程：包的旅程是 Guest → 内核 → QEMU 用户态 → 内核（TAP）→ 物理网卡，每跳都可能被调度器晾在一边，高 PPS 下延迟抖动明显。

税三 · 多余的数据拷贝

以 TAP 收包为例，QEMU 要先把包 read 进自己的缓冲区，再拷进 Guest 内存——RX 方向凭空多一次全包拷贝（下一节有逐包的账）。

vhost 的解法不动契约、只换执行者：队列格式、描述符语义、特性协商全部照旧，Guest 驱动甚至不知道后端换了人；变的是消费队列的代码运行在哪里——内核里（vhost-net）、另一个用户进程里（vhost-user）、或者网卡硬件里（vDPA）。QEMU 退居二线，只负责启动时的配置下发和热迁移等控制面事务。

关键前提：Guest 的物理内存对后端必须可达。virtqueue 和数据缓冲都在 Guest RAM 里，后端要能把 Guest 物理地址（GPA）翻译成自己能访问的地址——这是后面 VHOST_SET_MEM_TABLE 和 vhost-user 必须共享内存（memfd／大页）的根本原因。

    提示：kick 通知（写 doorbell / eventfd）只是「按门铃」，真正的数据从不经过通知通道——后端是自己去环里取的。所以 kick 可以合并、可以丢弃重复，队列状态本身才是事实来源。

    通知机制：eventfd 组成的「门铃 + 回铃」

    • Kick（Guest → 后端）：Guest 驱动写 virtio 通知区，QEMU/后端把这动作转成对一个 eventfd 的写。后端（内核线程或 DPDK 轮询）由此得知队列有新元素——vhost-user/DPDK 场景干脆轮询环的 idx，连门铃都省了。
    • Call（后端 → Guest）：后端处理完后写另一个 eventfd，它在 KVM 里注册为 irqfd，直接由内核注入虚拟中断，绕过 QEMU。
    • 抑制优化：VRING_AVAIL_F_NO_INTERRUPT / VRING_USED_F_NO_NOTIFY 标志位让双方在批量处理时互相少按门铃，这是高吞吐下不靠中断风暴的关键。

    拷贝账：性能差异最直观的一把尺

    「快多少」受包长、特性协商、机器配置影响很大，空泛的倍数没有意义；但每个包被整包拷贝几次是体系结构决定的、可核查的事实。下图是 TAP 网络场景下已核实的拷贝次数（QEMU/Cloud Hypervisor 的 TAP 路径与内核 vhost-net 源码级结论）：

    TX（Guest → 网卡）拷贝次数 RX（网卡 → Guest）拷贝次数
    • 纯 QEMU + TAP：TX 时 iovec 直指 Guest 内存、writev 由内核拷进 skb，1 次；RX 时 QEMU 先 read 进自有缓冲、再拷进 Guest，2 次——多出的那次来自 QEMU 通用 NetClient 抽象要求后端先把包读进自己的缓冲再分发。
    • vhost-net（默认 copy 模式）：内核线程在 Guest 内存与 skb 之间直接搬运，TX/RX 各 1 次，且省掉了 QEMU 的调度与 VM Exit 往返。其可选的零拷贝 TX（模块参数 experimental_zcopytx）默认关闭——省拷贝要付出完成通知与缓冲回收复杂度的代价，社区多年未将其转正。
    • vhost-user + DPDK：后端把 Guest 内存当作自己的 mbuf 池，网卡 DMA 直达 Guest 缓冲，0 次拷贝；代价是必须大页/共享内存、CPU 轮询忙等。

        所有 vhost 方案共同的账

        议题说明
        后端即全权代理后端能读写全部 Guest 内存（这是它干活的前提）。vhost-user 后端进程一旦被攻破，等同于拿下 Guest——选型时要把后端纳入可信计算基，DPDK/SPDK 进程的隔离与最小权限不能省。
        热迁移要对齐特性迁移前后端协商出的特性集（如可合并 RX 缓冲、多队列数）必须兼容；vhost-user 的后端状态不在 Guest 内存里，迁移/快照时要后端自己配合（如 OVS-DPDK 的连接状态、SPDK 的卷状态）。
        快照与恢复的边界以沙箱场景为例：vhost-user 后端的状态不进内存快照，恢复目标机上后端必须先就位；Cloud Hypervisor 还因此把 vhost-user 设备的恢复模式锁定为整内存预拷贝（eager），不支持按需懒恢复。
        共享内存是硬门槛vhost-user 要求 Guest 内存以共享方式映射（shared=on / 大页），与内存加密型机密虚拟机（SEV-SNP 等明文共享受限场景）、内存超分等特性存在天然张力，需要逐项确认兼容性。
        排障可观测性变差数据面离开 QEMU 后，tcpdump 抓点、计数、限速的位置都随之后移：vhost-net 看 TAP 口，vhost-user 要看后端（OVS-DPDK/SPDK）自己的统计与工具链。

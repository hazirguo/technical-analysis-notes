01

背景：代理本来不会「打洞」，CONNECT 是补上的那块

从只能转发 HTTP，到能承载任意 TCP —— 一条方法如何改变代理的定位

起点

HTTP 代理最初只做一件事：替你取网页

早期代理处理的是明文 HTTP：客户端把完整 URL 写进请求行 GET http://example.com/a.html，代理解析、代为请求、回传响应。它必须看懂每一个请求。

HTTPS 出现后这套逻辑失效：TLS 要求客户端与源站端到端握手、校验源站证书，中间任何一方插手解析都会破坏加密与身份校验。代理既不能代发，又不能缺席（企业网、受限网络里客户端根本无法直连源站）。

解法

CONNECT：不解析，只接通

CONNECT 换了思路：代理不再「代发请求」，而是「代建连接」。客户端明文告诉代理目标 host:port，代理完成鉴权与拨号后回 200，随即把两条 TCP 连接对接成一条隧道。

隧道里跑什么协议代理一概不管 —— 这让它从「HTTP 专用中继」升级为「通用 TCP 穿透原语」，也成为后来 WebSocket、HTTP/2、MASQUE、服务网格 HBONE 共同的地基。

演进时间线

2000
RFC 2817 §5（2000 年 5 月）首次系统描述 CONNECT 与 TLS 隧道化（tunneling），与 Upgrade 机制一同提出。
2014
RFC 7231 → 现 RFC 9110 §9.3.6 正式规范 CONNECT 语义：请求目标为 authority-form（host:port），成功后连接转为隧道模式。
2015
HTTP/2（RFC 7540 §8.3，现行 RFC 9113 §8.5） CONNECT 迁移到伪头：:method CONNECT + :authority，一条连接可多路复用多条隧道流。
2018
RFC 8441 扩展 CONNECT 承载 WebSocket（:protocol websocket），免去 Upgrade 流程。
2022
RFC 9297 / 9298（MASQUE） 推出 HTTP Datagrams 与 CONNECT-UDP：CONNECT 家族从 TCP 扩展到 UDP，支撑代理 QUIC、DNS、VoIP 流量。
2023
RFC 9484 推出 CONNECT-IP：隧道进一步扩展到 IP 层，可代理整包 IP 流量（VPN 类场景）。
今天
基础设施内建 Istio ambient 的 HBONE、Cloudflare Tunnel、沙箱网关（Kuasar Router → node proxy）都以 CONNECT 作为节点间的一次性隧道握手。
02

为什么必须有 CONNECT？缺一条都不行

直接把 ClientHello 发给代理，为什么行不通

原因 1 · 寻址

不说，代理不知道连谁

客户端的 TCP 只连到代理自己。若直接发 TLS ClientHello，代理无从得知目标域名与端口。靠嗅探 SNI 猜更不可靠：ECH 会加密 SNI，非 TLS 协议根本没有 SNI，端口也猜不出。CONNECT 在加密前明文写清 host:port。

原因 2 · 模式切换

代理要分清「代发」还是「打洞」

GET http://… 是让代理取资源（要解析）；CONNECT host:port 是让代理开管道（不解析）。没有这个专门方法，代理收到字节流无法决定工作模式。CONNECT + 200 就是那个明确的切换信号。

原因 3 · 管控前置

拨号之前先过闸

CONNECT 给了代理在连接源站之前检查的机会：身份认证（407）、域名白名单、端口策略（只放 443？）。不过闸直接拒绝，根本不去连源站 —— 审计与访问控制都锚在这一步。

一句话：CONNECT 不是在建客户端→代理的 TCP（那条早已由 SYN 建好），它是一条带内控制指令 —— 用它，代理不用懂 TLS，也能让两端端到端握手，且证书校验完整保留。这与 SOCKS5 的 CONNECT 命令是同一个思想，只是换成了 HTTP 写法。

05

应用场景：凡是「代理看不懂、又必须穿过代理」的流量

CONNECT 的通用价值 = 在只能说 HTTP 的代理面前，合法地要一条不被解析的管道

场景 1 · 主场

HTTPS 上网

浏览器、curl、git、npm、pip、Docker 拉镜像走 HTTPS 仓库 —— 全部先 CONNECT 到 :443 再 TLS。企业网审计、合规出口、白名单管控都锚在 CONNECT 这一步。

CONNECT registry-1.docker.io:443
场景 2 · 同类

其他 TLS 协议

凡 TLS 套壳者皆然：IMAPS :993、SMTPS :465、LDAPS :636、MQTTS :8883、AMQPS :5671，以及 MySQL / PostgreSQL / Redis 的 TLS 模式。

CONNECT mail.example.com:993
场景 3 · 穿透

SSH 与数据库直连

corkscrew / proxytunnel 帮 ssh 走 HTTP 代理；数据库客户端同理。也正因如此，企业代理默认只放行 443/8443，22、3306 一律 403 —— 放开等于打通内网 TCP。

CONNECT github.com:22
场景 4 · 长连接

WebSocket

wss:// 先 CONNECT 建隧道再 TLS 再 WS 握手；HTTP/2 则用 RFC 8441 扩展 CONNECT（:protocol websocket）在单条流内直接承载，不再 Upgrade。

场景 5 · UDP

CONNECT-UDP / MASQUE

RFC 9298 在 HTTP/3 流里封装 UDP：代理 QUIC、DNS、VoIP、游戏流量。CONNECT 从 TCP 隧道进化为 UDP/IP 隧道（CONNECT-IP，RFC 9484）。

场景 6 · 基础设施

服务网格与沙箱网关

Istio HBONE：ztunnel 间以 HTTP/2 CONNECT 建 mTLS 隧道，:authority 带原始目的地、证书带 SPIFFE 身份。Kuasar：Router → node proxy 一请求一条一次性 CONNECT，鉴权/唤醒绑在握手上，200 后裸字节直达 guest。Cloudflare Tunnel 同理。

反向代理需要 CONNECT 吗？ 普通反向代理（如 Nginx proxy_pass）不需要：它终结 HTTP、后端静态已知，直接 dial 即可。需要 CONNECT 的是隧道型网关：不终结协议、后端动态路由、且要在任何数据到达后端之前完成鉴权、路由与唤醒 —— CONNECT 握手就是放这些信息的唯一带内位置。node proxy 本身两种都吃（CONNECT 走隧道、普通 HTTP 走转发），用 CONNECT 是 Router 的架构选择，不是协议硬限制。

06

抓包与 MITM：能抓到 HTTPS 报文吗？

能抓到包，但默认只能看到三层东西 —— 明文在哪，取决于你站在哪、是否终结 TLS

第 1 层 · 明文

CONNECT 本身

客户端→代理段是明文 HTTP：目标域名:端口、代理认证、放行结果一目了然。这是定位「连不上」最先看的报文。

第 2 层 · 元数据

TLS 握手

ClientHello 的 SNI、版本、套件；ServerHello 与证书（TLS 1.3 证书已加密；ECH 会连 SNI 一起加密）。注意抓包里目标 IP 是代理 IP，不是源站。

第 3 层 · 密文

Application Data

真正的 GET / Header / 正文都在 TLS 记录里，只能看到长度、方向、时序。只靠服务器私钥也解不开 TLS 1.3（ECDHE 前向保密）。

想看到明文，只有两条正路

  • 会话密钥解密：让浏览器/curl 导出 SSLKEYLOGFILE，Wireshark 加载后解密自己抓的包 —— 调试自有客户端的首选。
  • MITM 代理解密：mitmproxy / Charles / Fiddler + 客户端预装其 CA。代理把一段 TLS 拆成两段（会话 ① 对客户端用自签假证书、会话 ② 对源站用真证书），自己成为两段端点，明文只在代理内部可见。证书锁定（pinning）的应用会直接失败。

关键澄清：MITM 代理与 HTTP 代理是同一个节点的两个维度 —— 「HTTP 代理」按客户端如何与它说话分（CONNECT），「MITM」按它拿到隧道后盲转还是解密分。普通代理 = HTTP 代理 + 盲转；MITM 代理 = HTTP 代理 + 解密模式。

透明 MITM 插在「位置 A」：客户端与 HTTP 代理之间

  • 劫 8080，不是 443：这段流量目标端口是代理端口，先到的是 CONNECT 不是 ClientHello，只劫 443 的经典透明 MITM 在这里直接失效。
  • 先当代理，再当服务端：先解析 CONNECT 并转发给上游真代理、等 200 回来，再拦截后续 TLS、用假证书终结。
  • 位置 B 更顺：插在代理与源站之间时 CONNECT 已被消费，只剩纯 TLS 到 :443，就是经典透明 MITM 的主场。
  • 两种位置都要求客户端信任 MITM CA；只被动 tcpdump 不终结 TLS，则哪里都看不到明文。
07

常见问题

把前面几轮最容易混淆的点一次说清

CONNECT 是建到代理还是源站？

发给代理，目标写源站。客户端的 TCP 只连代理，CONNECT 是对代理说「帮我去连 example.com:443」。代理自己拨号源站并回 200；源站从头到尾没见过 CONNECT。多级代理时，每一跳的 CONNECT 收件人都是下一跳代理。

CONNECT 用的 HTTP/2 / HTTP/3 时长什么样？

没有请求行，改用伪头：:method: CONNECT、:authority: example.com:443，HTTP/2 还省略 :scheme/:path（扩展 CONNECT 除外）。语义不变：2xx 响应后该流转为隧道。好处是一条连接可多路复用多条隧道，HBONE 正是靠这一点摊薄 mTLS 握手成本。

隧道里能跑 HTTP/2 / HTTP/3 到源站吗？

能。隧道是字节级的：TLS 协商出 ALPN 是 h2 就跑 HTTP/2 帧，是 h3 则……注意 HTTP/3 跑在 QUIC/UDP 上，而经典 CONNECT 只建 TCP 隧道 —— h3 穿代理要走 CONNECT-UDP（MASQUE），不能直接塞进 TCP 隧道。

CONNECT 失败和 TLS 失败怎么区分？

看失败发生在哪一段：收到非 200 的 HTTP 响应 = CONNECT 阶段失败（认证/策略/代理连不上源站）；收到 200 之后握手告警或中断 = TLS/源站问题，与代理无关（代理只搬字节）。抓包时先定位这条分界线，能省掉一半排查时间。

代理怎么知道隧道该结束了？

任意一端关闭 TCP，代理就关闭另一端并释放两条连接（半关闭时应转发 FIN 后再全关）。隧道没有 HTTP 层的 Content-Length / 分块结束标记 —— 连接关闭就是唯一的结束信号，这也是 CONNECT 隧道天然是「一请求一连接」的原因。
